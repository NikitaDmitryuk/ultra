# Работа Codex в ultra

Лимит этого файла — 120 строк. Подробности размещай в тематической документации.

## Навигация

ultra — Go-проект: relay с ролями bridge/exit, SSH-установщик и Telegram-бот.
Перед изменением прочитай только относящиеся к задаче документы:

- [ADR](docs/adr/README.md): долгосрочные решения и правила их отбора.
- [Архитектура](docs/architecture.md): потоки данных, границы и источники состояния.
- [Разработка](docs/development.md): проверки, SQL, миграции, встроенные ресурсы.
- [README](README.md): сборка, установка, эксплуатация и API.
- [Перенос bridge](docs/bridge-migration.md): подготовка, cutover и rollback между серверами.
- [Мобильная установка](deploy/MOBILE_INSTALL.md) и [TLS](deploy/TLS.md).

## Рабочий цикл

1. Уточни ожидаемый результат по задаче, проверь `git status` и релевантные исходники.
2. Прочитай документы по затрагиваемой теме. Сверяй описание поведения с кодом.
3. Внеси минимальное достаточное изменение, сохраняя чужую незавершённую работу.
4. Выполни проверки по [матрице разработки](docs/development.md), проверь diff.
5. После значимого проверенного изменения и перед завершением оцени новый контекст
   по правилам ниже. Обновление документации выполняй в той же задаче без отдельного напоминания.
6. В ответе укажи результат, выполненные и пропущенные проверки, а также обновлённый
   контекст либо краткую причину, почему нового устойчивого знания нет.

## Субагенты и выбор моделей

Для независимых частей работы разрешено до **5 одновременно работающих субагентов**
плюс координатор. Лимит общий для дерева делегирования; фактический предел среды
имеет приоритет. Не запускай агентов ради заполнения слотов и не обходи ограничения.
Координатор сохраняет модель чата; модель каждого нового субагента выбирает явно:

| Задача | Модель | Reasoning effort |
| --- | --- | --- |
| Механические правки, поиск потребителей, запуск готовых проверок | `gpt-6-luna` | `low` |
| Небольшая локальная правка по точному заданию, простой тест, документация | `gpt-6-luna` | `medium` |
| Обычная разработка и исправление воспроизводимого дефекта | `gpt-6.1-sol` | `low` |
| Несколько подсистем, конкурентность, данные, квоты, recovery/rollback | `gpt-6.1-sol` | `medium` |
| Неясная архитектурная проблема или сбой, не решённый Sol | `gpt-6-astra` | `medium` |
| Любое ревью изменений и независимая итоговая приёмка | `gpt-6-astra` | `high` |

Ревью всегда выполняет отдельный агент на самой сильной доступной модели, сейчас
`gpt-6-astra`; автор не заменяет независимого ревьюера. Критичность важнее размера diff:
изменения секретов, прав доступа, данных и production не поручай Luna даже при малом объёме.
Если задача оказалась сложнее или повторная попытка не дала новых фактов, передай её
следующему уровню с воспроизведением и результатами; не повторяй вслепую те же действия.
Начинай с указанного effort; `high` вне ревью и `xhigh`/выше требуют конкретной
нерешённой проблемы. Не повышай модель только из-за длительного ожидания команды.
Выбирай только модели и effort, доступные инструменту запуска. При недоступности модели
используй более сильную доступную, а если её нет — сильнейшую доступную; явно сообщи замену.
Для ревью при любом fallback выбирай только сильнейшую доступную модель.
Сопоставление обновляй по доступному каталогу и [официальному описанию моделей](https://developers.openai.com/api/docs/models/all), а не по предположению о номере версии.
Проектный лимит и экономичные значения по умолчанию задаёт `.codex/config.toml`;
правила выше уточняют выбор по задаче. Доступные слоты проверяй в текущем сеансе.

Каждому агенту задай результат, владельца файлов/подсистемы, ограничения и проверки.
Один файл одновременно меняет один исполнитель; общие контракты согласует координатор.
Изменения production выполняются последовательно одним назначенным исполнителем.
Тяжёлые сборки, VM и нагрузочные тесты согласуй по CPU/RAM; пять агентов не означают
пять параллельных тяжёлых прогонов. Агент возвращает изменения, доказательства проверок
и оставшиеся ограничения; координатор проверяет интеграцию и не повторяет неизменённые проверки.

## Что сохранять

Факт должен одновременно соответствовать всем условиям:

- Специфичен для ultra и полезен за пределами текущей задачи.
- Подтверждён исходником, тестом или принятым решением; источник можно найти в репозитории.
- Помогает избежать ошибки или повторного нетривиального исследования.
- Не дублирует актуальное описание в другом месте.

Формат: текущее поведение или ограничение → практическое следствие → источник.
Для воспроизводимой ловушки добавь способ проверки или обхода.
Неизвестные причины прошлых решений не восстанавливай догадками.

Сначала исправь существующий тематический раздел. Самостоятельная новая тема может
получить страницу в `docs/`, но сразу добавь ссылку из доступной навигации.
При изменении поведения исправь или удали устаревшее описание; объединяй дубли.
Повторяемое требование по возможности закрепи тестом, а в документе объясни его смысл.

Не сохраняй общие советы по программированию, пересказ функций, дневники сессий,
планы задач, логи, отчёты отдельных запусков, временные ошибки окружения, секреты,
данные пользователей и неподтверждённые гипотезы. Ход задачи и handoff остаются в задаче/PR.
В tracked-документах и примерах не указывай реальные адреса, домены, локации, ID или тарифы
действующей инфраструктуры. Используй RFC 5737, `example.com`/`example.net`, нейтральные роли и явные placeholders.
Если полезного нового знания нет, документацию не меняй: обязательна оценка, а не запись.

## Куда сохранять

- Устройство системы и устойчивые границы — в архитектуру.
- Воспроизводимые особенности сборки, тестирования и изменения кода — в разработку.
- Пользовательское поведение и эксплуатацию — в существующий README или инструкцию `deploy/`.
- Границы, хранение, внешние контракты, доверие и развёртывание — в актуальную тематическую страницу.
- Документация описывает действующий проект. Долгосрочные решения и обоснованные альтернативы — в [ADR](docs/adr/README.md); временные решения, планы и отчёты отдельных задач туда не включай.

## Проверки и границы

- `make harness-check` проверяет структуру документации; её полезность проверяй по смыслу.
- `make test` без `DATABASE_URL` пропускает DB-интеграцию. Не называй это полной проверкой БД.
- DB-тесты запускай только с явно выделенной тестовой БД: `db.Open` применяет миграции.
  Для обычных локальных проверок исключи случайно унаследованный `DATABASE_URL`.
- Генерируемые SQLC-файлы меняй через исходные SQL и генерацию; см. руководство разработки.
- Не запускай установку, SSH, изменение firewall, выдачу сертификатов или другие операции
  на рабочих узлах без авторизации задачи. Команды `make install` и эксплуатационные проверки
  не являются локальными проверками кода.
- Не читай и не сохраняй значения из `.env`, `install.config`, приватных ключей и окружения.
- Не делай commit/push, релиз или переписывание Git-истории без соответствующего поручения.

## Graphify

Если локальный индекс `graphify-out/graph.json` уже есть, используй его для навигации
по связям. Это необязательный генерируемый артефакт: он может устареть или пропустить связи.
Проверяй утверждения по исходникам и тестам; отсутствие ребра не доказывает отсутствие зависимости.
Не требуй установки Graphify для обычной задачи и не сохраняй его отчёты или историю запросов
как канонический контекст. Обновление индекса не заменяет редактирование документации.
