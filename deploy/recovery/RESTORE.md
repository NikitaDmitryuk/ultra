# Восстановление подготовленной VM

Операторская машина — Linux amd64/arm64; воспроизводимая среда учения — Ubuntu
24.04. Для штатного Ansible-восстановления нужны Python 3.12–3.14, age 1.x (включая `age-keygen`) и OpenSSH client 8+.
На Ubuntu зависимости устанавливаются одной командой:
`sudo apt-get update && sudo apt-get install -y python3 age openssh-client ca-certificates`.
Бинарник `ultra-install` содержит recovery-скрипты, но вызывает эти внешние
инструменты; полностью автономным бинарником он не является. На других ОС
операторский путь не проверен.

Ansible заранее устанавливать не требуется. После расшифрования и проверки
поколения операторский адаптер берёт сохранённые `runtime/requirements.lock` и
wheel-файлы из проверенного артефакта, создаёт приватный venv и передаёт его
исполнитель явно всем Ansible-этапам. `/opt/ultra-ansible` на машине оператора не
нужен. Восстановление не скачивает текущие версии из pip/Galaxy. Если операторская
архитектура отличается от сохранённых wheel-файлов, передайте полный проверенный
комплект с подходящим runtime через `restore --release-dir /private/release`.
При отсутствии runtime в прежнем поколении этот аргумент также обязателен.


`ultra-install restore --config /private/restore.json` использует встроенные
скрипты восстановления. Для bridge поддерживается чистая Ubuntu 24.04 с root SSH
и Python 3; устанавливаются PostgreSQL client tools, nginx, certbot и остальные
зависимости приложения. PostgreSQL 16 отдельно подготавливается Ansible на
`database_target`; IPv4 должен совпадать с `database_host`. Restore допускается
только в пустую выделенную базу: скрипт проверяет отсутствие пользовательских
таблиц и отказывается перезаписывать непустую БД. Пароль приложения не включается
в restore plan и не передаётся в argv/logs.
Архитектура VM должна совпадать с ELF-артефактом выбранного поколения (amd64/arm64).
Поле `new_bridge_provider` обязательно: независимость копий пересчитывается для
нового провайдера только после подтверждения доставки.
VM предоставляет оператор: команда не покупает серверы. Режим ingress выбирается явно;
без `ingress_mode` сохраняется совместимость с прежним forwarding через отдельный ingress-узел.

[Пример restore.json](restore.example.json) содержит все обязательные поля.
Рядом с выбранным `backup-*.age` должен находиться указанный им `artifact-*.age`.
JSON-конфигурация, fencing-файл и приватные ключи должны иметь режим 0600;
операторский каталог состояния — 0700. SSH использует только явно заданный
ключ и предварительно проверенный known_hosts, без TOFU и ssh-agent.

Перед запуском отключите старый bridge и заполните
[отдельное подтверждение fencing](fence.example.json): адрес старого bridge,
точный SSH host новой VM и Unix timestamp проверки. Подтверждение действительно
один час и проверяется перед каждым этапом. Команда не заменяет проверку
отключения старого сервера: два производителя состояния недопустимы.
Отсутствующее, просроченное, датированное будущим или привязанное к другим адресам
подтверждение останавливает основной запуск; команда не обновляет его автоматически.

Обычное восстановление требует нового IPv4. Плановый перенос с сохранением
перемещаемого адреса допускается только с `migration_identity`: различающиеся
`source_machine_id` и `target_machine_id` (32 hex-символа), а также различные
`source_ssh_endpoint` и `target_ssh_endpoint`. Тот же объект должен присутствовать
в свежем fencing-подтверждении, а target endpoint — совпадать с SSH-целью плана.
Идентичность включается в ID операции; целевой helper сверяет локальный machine-id
перед каждым этапом. Проверка отключения прежнего primary остаётся обязательной;
одного совпадающего публичного адреса для такой миграции недостаточно.

Предварительная команда `ultra-install restore --config /private/restore.json
--check` проверяет расшифровку, manifest и pinned SSH без установки или переключения.
Она временно расшифровывает поколение только на машине оператора. Приватный age
identity не передаётся ни новой VM, ни exits.

Основная команда проверяет manifest обоих архивов и capability `service-access-v1`,
маскирует прикладные и автоматические units до переноса состояния, восстанавливает
роли и логический dump PostgreSQL. До изменения служебного состояния содержимое
каждой публичной таблицы сравнивается с отдельным контрольным импортом. Реальная
версия схемы должна укладываться в границы release-manifest.
Активация и её повтор при resume проверяют конфигурацию nginx и выполняют reload:
установка пакета могла запустить nginx ещё до восстановления его конфигурации.

Опубликованные адреса bridge обновляются только в совпадающих собственных
endpoint-записях; UUID, токены, SNI и адреса exits сохраняются. Bridge подключается
к выделенной БД через `ultra-db-tunnel.service`; Ansible применяет туннель к
`database_host` до запуска relay. Backup хранит `/etc/ultra-db-tunnel` и unit туннеля.
Физическая PostgreSQL-репликация не используется. Для управляемого Vultr exit проверяются
instance, IP и собственная firewall group, затем добавляются правила нового
bridge для SSH и фактического tunnel-порта. Старые правила не удаляются.

В режиме `ingress_mode: "forward"` nginx отдельного ingress-узла переключается только при подтверждённом владении конфигурацией; ошибка
`nginx -t` или reload возвращает прежние файлы. DNS остаётся прежним. После проверки
публичного HTTPS включаются backup/controller timers. Готовность требует online
runtime, свежей encrypted backup и готового независимого мониторинга.

В режиме `ingress_mode: "direct"` поле `ingress` не требуется. `public_host` —
полное имя edge, `subscription_domain` — полное имя sync из сохранённой DNS policy.
Оба имени переводятся на новый bridge. Policy `/etc/ultra-recovery/dns.json`,
ключ `dns-api-key` и receipt `dns-receipt.json` восстанавливаются из проверенной
копии. Перед изменением DNS проверяются сертификаты обоих имён на новом IP,
HTTPS `/healthz` подписки и свежее fencing. Затем выполняется owned DNS reconciliation,
ожидание authoritative/resolver convergence и публичная TLS/HTTPS проверка.
При частичной ошибке автоматизация не включается; повтор использует сохранённый
DNS receipt, не возвращая записи на отключённый bridge. Даже завершённый DNS этап
при resume повторно проверяется. Direct mode требует поколения с этой DNS policy
и конфигурацией обоих ingress на самом bridge; старый forwarding-only архив автоматически
в новую схему не преобразуется.

Certbot lineages восстанавливаются перед активацией: backup хранит содержимое
символических ссылок `live`, поэтому restore создаёт проверенные `archive` PEM и
четыре относительные `live` ссылки, необходимые для последующего renew. Это работает
и для прежних копий без `archive`; существующая история не перезаписывается.
Обрабатываются только сохранённые renewal-конфигурации со стандартными путями
`/etc/letsencrypt/{live,archive}/<lineage>`. Неполная копия, чужая ссылка или изменение
PEM останавливает восстановление; прерванное создание ссылок безопасно повторяется.
Новые сертификаты и ключи при этом не выпускаются.

При прерывании повторите ту же команду с тем же поколением и свежим fencing.
Идентификатор операции привязан к ciphertext и адресам назначения; receipts
сохраняются в операторском `state_dir` и `/var/lib/ultra-restore` на VM.
При ошибке CLI сообщает безопасные `stage` и `code`; после проверки приватного
каталога те же поля сохраняются в `<state_dir>/<restore_id>/last-error.json`.
Успешное завершение повторного запуска удаляет этот файл. Неизвестные ошибки
обобщаются; команды, приватные значения и stderr удалённого процесса не публикуются.
Завершённые этапы сверяют machine-id, файлы артефактов и PostgreSQL identity/schema.
Работающая БД не импортируется повторно. Постоянные systemd override-параметры
хранятся в `/etc/ultra-recovery/restored-environment`, который входит в следующую
резервную копию. Приватные staging-каталоги сохраняются для разбора/возобновления;
они содержат расшифрованные данные и не предназначены для публикации.

## Операторский recovery key

`ultra-install recovery-key init --identity /private/identity.txt
--recipient-output /private/recipient.txt` создаёт ключ только при его отсутствии.
Повторный запуск проверяет существующую пару; если запись публичного recipient
была прервана, она завершается без смены ключа. Несовпадающий recipient — ошибка.

После независимого сохранения извлеките копию в другой файл и выполните
`ultra-install recovery-key verify --identity /private/identity.txt
--extracted-identity /private/extracted.txt --bundle /private/generation/backup.age
--receipt /private/key-proof.json`. Проверка расшифровывает оба архива извлечённой
копией. Receipt доказывает работоспособность предоставленной копии; происхождение
из независимого хранилища оператор подтверждает отдельно. Одна inode или hardlink
не считается отдельной извлечённой копией.

Перед включением резервного копирования восстановление возвращает в локальный
репозиторий исходный зашифрованный артефакт выбранного поколения. Повторное age-шифрование
тех же бинарников создаёт другой ciphertext под тем же именем версии, который
неизменяемый репозиторий exit обязан отвергнуть. Поэтому оператор повторно проверяет
исходное поколение своим age-ключом и передаёт только ciphertext; при продолжении
после неудачной попытки прежний локальный cache сохраняется отдельно.


Операторская команда восстановления применяет фиксированные playbook’и `restore`
и `restore-peer` из своего проверенного комплекта. Стадии расшифрования, проверки
manifest, PostgreSQL identity, сохранения Certbot lineage и ownership остаются
прикладными проверками. Пакеты, сервисы, firewall и переключение принадлежащих
ultra конфигураций применяет Ansible. Повтор завершённой стадии снова проверяет
данные и приводит службы к требуемому состоянию.

Для reseed SSH credentials берутся из проверенного локального staging выбранного
поколения. Отсутствующая или изменённая относительно manifest identity/pins
останавливает операцию; новые pins автоматически не принимаются. Конфигурация
изолированного учения задаёт `isolated_peer_addresses`: обращение к peer вне этого
списка прекращается до запуска Ansible. Это дополнительная проверка стенда,
а сетевой запрет исходящих production-соединений остаётся обязательным.
