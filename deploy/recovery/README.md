# Резервное копирование и независимый монитор

Полный комплект копий, контроллера и мониторинга устанавливает [план версии 2](../../docs/automation.md).
Низкоуровневые команды ниже предназначены для диагностики и обслуживания отдельных
компонентов; они не заменяют итоговую проверку готовности штатного установщика.
Операторский CLI восстановления описан в разделе «Штатное восстановление» ниже.


`recovery.py` создаёт согласованный логический `pg_dump -Fc`, выбранные настройки
и ключи, шифрует их публичным age-ключом оператора и передаёт поколения на exit.
Приватный age-ключ остаётся у оператора. Бинарники входят в отдельный неизменяемый
артефакт по хешу версии и не передаются заново каждые две минуты.

## Подготовка

На bridge и exit нужны Python 3, age и достаточно диска. На bridge нужны
PostgreSQL tools (`pg_dump`, `psql`) и работающий `ultra-db-tunnel.service`,
который ведёт на выделенный DB primary. Отдельный локальный PostgreSQL standby
обновляется через этот туннель; прикладные запросы и миграции идут на primary.
Временный `PGPASSFILE` с режимом 0600 предоставляет libpq пароль из runtime DSN,
пароль не передаётся в argv. Для монитора нужен curl. Скрипты, units и права применяются ролями Ansible `recovery` и `monitor`.
Каталоги настроек и хранения имеют `0700`, JSON и токены — `0600`, владельца root.
Runtime-контроллер выбирает топологию и проверяет доставку, но не устанавливает
пакеты и службы через вложенные SSH-команды. Обновление только release-owned
инструментов использует `recovery` в режиме refresh: пользовательские настройки
и секреты не перезаписываются.

На всех трёх узлах отдельно инициализируйте пустой каталог:

```sh
python3 /opt/ultra-recovery/recovery.py init --repository /var/lib/ultra-recovery --source bridge
```

По `backup.example.json` создайте `/etc/ultra-recovery/backup.json` **на bridge**.
`database_host` должен совпадать с IP выделенного PostgreSQL-сервера. В `optional_state_paths` укажите точный файл keyring подписок `/var/lib/ultra-relay/automation/subscription-keys.json`: он будет включён в зашифрованную age-копию после установки; не добавляйте весь каталог `automation`, содержащий также ключи провайдера.
Укажите существующие обязательные прикладные файлы и каталоги,
SSH-ключи backup-доставки и соответствующий `.pub`, известные host keys, spec, systemd environment/drop-ins,
Nginx, Certbot renewal, выбранный каталог `live/<domain>` и конкретный
каталог настроенного camouflage-сайта Nginx и каталог ACME-аккаунта, указанный в сохранённом renewal config. Один renewal config
не содержит закрытый ключ регистрации аккаунта: без выбранного каталога
`accounts/<CA>/directory/<account>` автоматическое продление после восстановления
может потребовать новой регистрации. Не выбирайте целиком `/etc/letsencrypt`. Отсутствующий обязательный
путь останавливает копирование. Если relay читает файл публичного SSH-ключа,
после восстановления обеспечьте чтение сервисным пользователем через владельца
или группу; одного наличия `.pub` с правами `0600 root:root` недостаточно. TLS symlink сохраняется как содержимое файла.
Не выбирайте `/etc`, `/var/lib` или целый `/root/.ssh`; только нужные Ultra пути.
При split routing отдельно добавьте каталог используемых geo-assets к артефактам.
Пути из `artifact_paths` исключаются из обычного state-пакета, даже если их родитель
выбран в `state_paths`: большие неизменяемые geo-файлы сохраняются по версии вместе
с бинарниками. При восстановлении перенесите их из `artifacts/` на исходные пути.

На bridge настройте SSH алиасы/адреса exit и strict known_hosts. Узел у независимого
провайдера назначается `required: true`: успешная передача только на основной exit не
подтверждает независимую копию.
Если доступен один exit у того же провайдера, разрешена обязательная копия на него
с `independent: false`. Она защищает от потери диска bridge, но не от общего отказа
провайдера. При появлении exit у другого провайдера назначьте его `required: true`
и подтверждайте независимость только после проверенной доставки на него.
Доставка не требует age-ключа расшифрования на exit. Репозиторий приёмника допускает
только проверенные имена; незавершённый поток не заменяет готовое поколение.
Bridge сохраняет артефакт, а временный зашифрованный пакет данных удаляется после
доставки. Имя пакета в `last-success.json` не означает наличие локальной копии.
Перед adoption проверяются SHA-256 обоих файлов на выбранном независимом обязательном
приёмнике через закреплённый SSH-доступ; одной квитанции доставки недостаточно.
Перед каждым поколением проверяется SHA-256 сохранённого артефакта бинарников;
одного наличия файла недостаточно. Повреждённый артефакт не подтверждает пригодную
копию. Записи файлов и каталога синхронизируются; повтор доставки после потери
ответа восстанавливает отметку свежести без замены готового поколения.
Состояние вместе с дампом БД ограничено 512 МиБ, распакованный артефакт — 1 ГиБ;
оба предела включают manifest и допускают до 20 000 файлов данных.
Каждый зашифрованный файл по-прежнему ограничен 512 МиБ и проверяется до доставки.
При передаче расшифрованного stage для восстановления состояние и артефакты
проверяются отдельно по тем же пределам; helper БД допускает до 2 ГиБ транспортного
архива с учётом tar/gzip, сохраняя предел самого дампа 512 МиБ.
Свободный запас приёмника перед загрузкой — минимум 512 МиБ + 1 ГиБ, чтобы после
приёма максимального файла оставался 1 ГиБ. Проверьте фактический размер с выбранными geo-assets.

Сначала вручную выполните `capture`, получите две копии и выполните `verify` с
операторским ключом **на доверенном узле оператора**. Затем активируйте backup timer
на bridge и prune timer на обоих exit. Последний пригодный пакет сохраняется даже
после истечения 14 дней; старые версии бинарников не удаляются автоматически.
Успех — `/var/lib/ultra-recovery/last-success.json`, свежесть считается от начала
снимка. Таймер каждые две минуты и лимит выполнения 170 секунд поддерживают цель
пяти минут только при исправной доставке; устаревание требует уведомления.
`diagnostic_status: true` на bridge дополнительно публикует
`/var/lib/ultra-relay/recovery-status.json` с владельцем `root:ultra-relay`, правами
`0640` и только полями `source`, `snapshot_at`, `completed_at`, `targets`, `independent`.
Подтверждение обновляется после успешной обязательной доставки. Relay читает его
без доступа к ключам или пакетам; возраст отсчитывается от начала снимка.

Для учения при работающем primary используйте `verify --test-stage --target <empty>`:
эта команда лишь проверяет и расшифровывает приватный тестовый каталог. Она не
переключает приложения или запись БД и не требует фиктивного подтверждения fencing.
Импорт для учения делайте только в новую выделенную тестовую БД.

Горячий `runtime.db` исключён: копирование открытого bbolt-файла небезопасно.
Build-каталоги `/var/lib/ultra-relay/releases` и `/var/lib/ultra-relay/candidates`
также исключены; действующие бинарники входят в отдельный артефакт, иначе накопленные
сборки быстро превышают ограничение размера пакета. Проверенный совместимый аварийный
бинарник храните отдельно, например в `/usr/local/libexec/`, и включайте в
`artifact_paths`, чтобы он сохранялся по версии, а не в каждом пакете.
Восстановление из SQL теряет локальные неподтверждённые измерения и резервы с
последнего пакета, но сохраняет подтверждённые настройки и расходы SQL. Для переноса
локального журнала остановите relay и перенесите его файл отдельно вместе с версией
бинарника. Не запускайте два relay с независимыми копиями одного журнала.

После перехода на durable accounting откат допускается только на проверенный
бинарник, понимающий account ledger, устойчивый AccountID и локальные резервы.
Старый бинарник до миграции 22 не становится совместимым после выгрузки очереди:
его обычные записи трафика не обновляют новый ledger, а смена UUID может вернуть
квоту. Подготовьте accounting-aware аварийный вариант до активации новой версии.
Закрытый журнал можно догрузить через `ultra-relay -drain-journal -spec ...
-runtime-state ...`: команда требует существующий файл bbolt и уже установленную
схему 22, подтверждает пакеты и финальные резервы; миграции не применяет.
Выгрузка сохраняет расход, но не разрешает запуск несовместимого старого кода.

## Восстановление

1. Зафиксируйте начало работ; подготовьте пригодную VM в РФ. Изолируйте старый
   primary от сети или выключите его у провайдера; одного неудачного SSH недостаточно.
2. Заберите выбранное поколение и указанный в нём `artifact-*.age`. На доверенном
   узле проверьте `verify --bundle ... --identity ...`. Команда проверяет оба архива.
3. Создайте приватный JSON `fence.json` с `source: "bridge"`,
   `confirmed_offline: true`, `confirmed_at: <Unix timestamp>`; срок — один час.
   Выполните `restore --bundle ... --identity ... --fence-file ... --target <empty>`.
   Расшифрованный результат содержит секреты: каталог нельзя публиковать.
4. До активации выполните `smoke.py --stage ...` на подготовленном узле PostgreSQL16.
   Команда использует новую случайную тестовую БД и удаляет только созданную ей БД.
   Для проверки relay доступны исходные абсолютные пути geo-assets/TLS; перенесите
   выбранные файлы на **изолированной VM** перед проверкой конфигурации.
5. Установите проверенные бинарники, выбранные файлы `state/` с исходными путями и
   правами. Создайте сервисного пользователя из `User=` unit и восстановите
   доступ этого пользователя к приватным файлам `/var/lib/ultra-relay` и keyring;
   распаковка тестового staging намеренно оставляет всё приватным оператору.
   Создайте роли SQL и новую пустую прикладную БД; восстановите дамп от
   postgres с `--no-owner --no-acl --role=<прикладная-роль>`, чтобы прикладная роль
   владела восстановленными объектами и могла применять последующие миграции. Исправьте DSN, SSH адрес bridge и public-host
   для новой VM; не меняйте UUID, токены подписок или keyring.
6. Nginx/Certbot используют `webroot /var/www/ultra-acme`. Сохраните этот путь и
   создайте пустой каталог через `install -d /var/www/ultra-acme`, если его нет;
   renewal config; публичный ACME challenge должен попадать на новый bridge.
   Проверьте `nginx -t`, затем запустите один relay, бот и копирование.
7. Проверьте доступ тестового пользователя, подписку, остатки квот, TCP/UDP и
   свежую независимую копию. Время до готовности измеряется с начала работы
   оператора и появления пригодной VM. Цель одного часа подтверждается учением.

## Независимый монитор

Независимый exit использует `monitor.example.json`, существующего Telegram-бота и выделенный
тестовый доступ с достаточной квотой. `ultra-monitor-probe.service` запускает
`ultra-client` из приватного JSON и предоставляет только loopback SOCKS.
Монитор проверяет HTTPS bridge, реальную HTTPS нагрузку через этот SOCKS и возраст
полученной независимой копии. Telegram отправляется напрямую из этого узла, без proxy
bridge. Монитор вызывает только `sendMessage`, не использует `getUpdates` и не
меняет webhook; основной бот продолжает получать пользовательские обновления.
В `token_file` укажите приватную копию токена существующего бота на exit:
новый бот и новый токен не нужны. Потеря Telegram сохраняет очередь,
429 соблюдает `retry_after`.
Основной монитор можно запустить на единственном доступном exit. Для копии у того
же провайдера задайте `backup_independent: false`: проверка называется
`backup_generation` и не сообщает независимость. Используйте существующий активный
администраторский доступ с доступной квотой для VPN-пробы; монитор не повышает квоты
и не создаёт пользователей. Исчерпание квоты делает пробу неисправной.

Основной exit использует `peer.example.json`, SSH-доступ к независимому exit и его heartbeat; монитор peer
не требует основного bridge. Heartbeat не сообщает готовность VPN, его задача —
обнаружить остановку независимого монитора и зафиксированные ошибки его отправки
в Telegram. Отсутствующий или устаревший heartbeat сообщает отказ монитора;
он не доказывает отдельный отказ доставки Telegram. При смене роли старые проверки
сбрасываются, а очередь уже созданных уведомлений сохраняется. Разрешите чтение heartbeat для
выбранного SSH пользователя. Units используют root по умолчанию и strict host keys.
После ручного контрольного запуска включите monitor timer, а на независимом exit — также probe
service. Состояние и очередь — приватные файлы `/var/lib/ultra-monitor/`.

Две последовательные проверки подтверждают отказ или восстановление. Первоначальный
успешный запуск не отправляет сообщение. Хранятся максимум 100 переходов состояния;
переполнение отмечается в состоянии монитора. При отключении независимого exit вместе с Telegram
доставка невозможна, основной exit продолжает собственную проверку и попытки уведомления.

Локальные тесты: `python3 -m unittest discover -s deploy/recovery -p 'test_*.py'`.

## Проверка данных и потоков в одноразовой VM

`vm_guest.py`, `vm_fixture.py`, `vm_verify.py` и `vm_generation.py` предназначены только для одноразовой
Ubuntu 24.04 VM. Это не установщик production: проверяющий заменяет DSN и внешние
адреса на loopback, поднимает локальный exit и блокирует исходящий трафик гостя,
кроме loopback и ответов текущего SSH. Не запускайте эти программы на рабочем узле.

Перед копированием состояния проверяющий останавливает и постоянно маскирует в
одноразовом госте backup/prune/reconcile, monitor/probe и Certbot services/timers.
Их восстановленные unit-файлы, `*.wants` и drop-ins остаются только в проверенном
stage и не заменяют маски. Поэтому сохранённые полномочия и enabled-ссылки не
запускают внешнюю автоматизацию. Маски в `/run` для этого недостаточны: unit из
`/etc` имеет более высокий приоритет. Дополнительные настройки запуска relay и
бота заменяются настройками учения. [Локальная регрессия](test_vm_guest.py)
проверяет копирование с существующими масками без запуска VM или systemd.
Фильтр действует только на `/etc/systemd/system`: одноимённые шаблоны контроллера
в `/opt/ultra-recovery` восстанавливаются как обычные неактивные артефакты.
Повторное тестовое поколение берёт эти unit-файлы из проверенного stage: живые
маски `/dev/null` не являются обычными файлами и не подлежат резервному копированию.
Для повторного копирования маски не снимаются.

HTTPS-цель [vm_fixture.py](vm_fixture.py) явно принимает только TLS 1.2 и новее;
учение не требует устаревших TLS 1.0/1.1. [Локальный тест](test_vm_fixture.py)
проверяет отказ старых протоколов и передачу с проверенным сертификатом по TLS 1.2/1.3
без запуска VM или привязки к публичному fixture-адресу.

Подготовьте QEMU (`-accel tcg` для программной эмуляции), приватный qcow2-диск,
SSH-ключ учения и Ubuntu cloud image. До начала измерения установите в госте
PostgreSQL 16, Nginx, Certbot, age, curl, Python, OpenSSL и iptables. После успешной
подготовки создайте `/var/lib/ultra-drill-ready`. Отключите внешний доступ VM на
уровне гипервизора или контейнера **до переноса расшифрованных данных**; оставьте
только локальный управляющий SSH. Гостевой firewall служит дополнительной границей.

На доверенной операторской машине выполните `verify --test-stage`, как описано
выше. Передайте приватный stage в `/root/ultra-drill-stage/`, четыре Python-скрипта и `recovery.py` — в
`/opt/ultra-drill/`, проверенный `ultra-client` — в `/usr/local/bin/ultra-drill-client`.
Соберите дополнительный verifier: `CGO_ENABLED=0 go build -o ultra-drill-state
./deploy/recovery/state-proof` и установите его в `/usr/local/bin/ultra-drill-state`.
Приватный age-ключ в гостевую VM не переносится. Начало измерения — готовая VM и
начало переноса проверенного stage. Внутри гостя:

```sh
sudo python3 /opt/ultra-drill/vm_guest.py --stage /root/ultra-drill-stage
sudo python3 /opt/ultra-drill/vm_verify.py
sudo python3 /opt/ultra-drill/vm_generation.py
```

Проверяющий повторно сверяет хеши manifest, восстанавливает текущую схему и сравнивает
данные доступа и учёта с независимым импортом того же дампа. Настоящие конфигурация
TLS, geo-assets, keyring и systemd восстанавливаются из пакета; внешние полномочия
остаются неактивными. Для каждого включённого production exit используется отдельный
локальный TLS-туннель на своём порту с исходным tunnel UUID: общий порт нарушил бы
уникальность включённых endpoint и не проверял бы многосерверную конфигурацию.
Исходные exit ID, связи квот и равенство всех таблиц проверяются до замены адресов.
Тестовые HTTPS-цель с проверкой тела и UDP-echo используют общий публично маршрутизируемый
fixture-адрес. Он присваивается только
интерфейсу `lo` гостя: это позволяет проверить неизменённый production exit, в котором
Xray блокирует приватные назначения. Внешний сетевой доступ остаётся закрыт;
эти запросы не отправляются внешнему сервису. Новое тестовое поколение шифруется отдельным одноразовым age-ключом и повторно
восстанавливается в новую БД с проверкой данных; операторский production ключ для
этого в гость не передаётся. Бот запускается с фиктивным Telegram-токеном;
это проверяет независимость HTTP от Telegram. Совместимый fallback использует тот
же bbolt-журнал; проверяются повторная передача данных, сохранение срока автономности
и отсутствие увеличения остатка квот. Verifier открывает журнал только после
остановки relay; приватный baseline не выводится и создаётся с `0600`.

Итог содержит только признаки проверок и время; данные пользователей и ключи не
выводятся. Отдельно измеряйте передачу stage и общую длительность до готовности всех
проверок: внутренний таймер не включает подготовку VM и передачу пакета. Учение в
локальной VM не подтверждает доступность новой VM в сетях РФ. После учения удалите
одноразовую VM, приватный диск, расшифрованный stage и временные ключи SSH; сохраните
зашифрованные поколения и воспроизводимые команды.

## Полное восстановление через штатный Ansible

[vm_topology.py](vm_topology.py) и [vm_acceptance.py](vm_acceptance.py) проверяют
штатные `apply`/`restore` на отдельных bridge, двух exit, чистой целевой VPN VM
и двух отдельных VM для исходной и восстанавливаемой БД. Сценарий обновлён
под dedicated DB, но полный прогон шести VM после изменения архитектуры ещё
не выполнен: успешные unit-проверки не подтверждают этот acceptance или время
восстановления. Старые результаты четырёх VM к новой топологии неприменимы.
У этого сценария собственные SSH/age-ключи и синтетические данные. Изоляция на
уровне QEMU ограничивает внешний доступ до запуска приложений; fixture-сервисы
заменяют внешние Telegram/HTTPS/DoH-цели. Оператор работает с неизменяемым комплектом
релиза и зашифрованным поколением, фактически доставленным независимому exit.

До запуска подготовьте только виртуализацию, базовую ОС и тестовые CA/потоки.
`vm_topology_fixture.py dependencies --workspace <private-directory>` запускает
тестовые пакеты и возвращает `prepared`/`pending`; продолжайте после `prepared: true`.
PostgreSQL primary устанавливается на отдельной целевой DB VM; восстанавливаемый
bridge получает клиент, SSH-туннель и заново инициализируемую standby-копию.
Nginx, Certbot, age и конфигурация
приложения входят в штатное восстановление и не устанавливаются заранее ради уменьшения измеренного
времени. Начало полного замера — оператор запускает восстановление при готовой
базовой VM; окончание включает проверку сервисов, данных, автоматизации и потоков.

Предыдущий сценарий `vm_guest.py` с заранее установленными службами подтверждает
восстановление данных и транспортные проверки, но не время полного развёртывания
чистой машины. Оба сценария не доказывают доступность будущей VM из сетей РФ.

## Офлайн-копия ключа восстановления

Без операторского age-ключа зашифрованные поколения восстановить нельзя. Сохраните
приватный файл ключа в защищённом менеджере паролей как файл-вложение либо на
зашифрованном съёмном носителе. Не переносите его на exit, в Git или в сообщения.
Проверка должна использовать файл, заново извлечённый из выбранного хранилища,
а не исходный файл с рабочего диска: права `0600`, приватный каталог, затем
`recovery.py verify --bundle ... --identity <извлечённая-копия>` на доверенной машине.
Успех подтверждает пригодность копии; содержимое ключа нигде не печатается.
Временный извлечённый файл удалите после проверки. Автоматическая копия на том же
диске не заменяет этот шаг оператора.

## Операторский VPN-доступ

Храните `operator_access.py`, проверенный `ultra-client` и профиль в постоянном
приватном каталоге операторской машины. Профиль должен иметь права `0600`, родитель —
`0700`; он использует действующий доступ и его квоту. Запускайте VPN в отдельном
терминале, затем SSH с проверенными host keys:

```sh
python3 /persistent/ultra/operator_access.py vpn --binary /persistent/ultra/ultra-client --profile /private/operator.json
python3 /persistent/ultra/operator_access.py ssh --socks 127.0.0.1:18928 --jump ultra-exit ultra-bridge
python3 /persistent/ultra/operator_access.py ssh --socks 127.0.0.1:18928 ultra-exit
```

Этот путь не зависит от процессов и профилей в `/tmp`. Он требует исправного VPN
пути; самостоятельным резервом при потере единственного bridge остаётся консоль
провайдера и процедура восстановления.

Для постоянного запуска можно использовать пользовательский systemd unit
`~/.config/systemd/user/ultra-operator.service`. Укажите абсолютные пути своего
каталога вместо `/persistent/ultra`; учётные данные остаются в приватном профиле:

```ini
[Unit]
Description=Ultra private operator VPN
StartLimitIntervalSec=60
StartLimitBurst=5

[Service]
Type=simple
ExecStart=/persistent/ultra/ultra-client -config /persistent/ultra/profile.json -socks 127.0.0.1:18938 -http 127.0.0.1:18939
Restart=on-failure
RestartSec=3
TimeoutStopSec=15
KillMode=control-group
UMask=0077
NoNewPrivileges=yes
StandardOutput=null
StandardError=null

[Install]
WantedBy=default.target
```

После `systemctl --user daemon-reload` и `systemctl --user enable --now
ultra-operator.service` процесс принадлежит user manager и запускается при входе
пользователя. Для SSH укажите `--socks 127.0.0.1:18938`. Проверяйте отдельно
`systemctl --user is-active ultra-operator.service` и передачу HTTPS через SOCKS:
активный процесс не подтверждает исправность туннеля. Если на устройстве работает
другой VPN с TUN, исходящее соединение оператора также может идти внутри него;
это проверяется `ip route get <адрес bridge>` и не создаёт независимый путь.

## Автоматическое подключение созданных exit

Производный кеш `/var/lib/ultra-bot/subscriptions.json` и диагностические receipts
`/var/lib/ultra-relay/recovery-status.json`,
`/var/lib/ultra-relay/recovery-reconcile-status.json` исключены из state-пакета.
Их атомарные обновления иначе нарушают проверку неизменности состояния между dump
и упаковкой. После восстановления PostgreSQL бот строит кеш заново; контроллер и
резервное копирование подтверждают новую готовность. Сохранённый старый healthy
receipt не доказывает исправность восстановленной системы. Подписки, квоты и ключи
остаются в БД и выбранных конфигурациях. Исключаются только эти точные пути,
одноимённые файлы в других каталогах сохраняются.

[Root reconcile](reconcile.py) работает отдельным systemd timer и не зависит от
процесса relay или ручного SSH оператора. После установки через штатный план версии 2 либо отдельной настройки
[service](ultra-recovery-reconcile.service), [timer](ultra-recovery-reconcile.timer)
и приватного [конфига](reconcile.example.json) новый exit, созданный через бота,
получает receiver, ротацию копий и монитор автоматически. При переносе bridge этот
комплект нужно восстановить и включить вместе с остальными эксплуатационными units;
один бинарник relay не устанавливает root-контроллер.

Контроллер читает только метаданные готовых cloud operations и включённых exit через
локальный PostgreSQL в транзакции `READ ONLY`; миграций и управляющих SQL-записей нет.
SSH использует существующий automation identity и индивидуальный `known_hosts`,
созданный установщиком для операции. Отсутствующий или изменившийся pin останавливает
настройку: контроллер не выполняет `ssh-keyscan`, `accept-new` или пересоздание VM.
Статические узлы явно перечисляются в конфиге с их реальным провайдером.
Независимость определяется отличием провайдера exit от `bridge_provider`, а не страной.

Установка ограничена известными путями, сверяет SHA, права и владельца; неизменный
клиентский бинарник повторно не передаётся. Новые receiver получают существующее
зашифрованное поколение через обычную capture/delivery процедуру. Адрес сначала
добавляется в пробную конфигурацию; постоянный `required` и `independent` включаются
после проверки свежести, источника и SHA обоих файлов — state и artifact. Source
`last-success.json` содержит имена и SHA этих файлов и идентификаторы доставленных
адресатов. Ошибка БД не означает удаление узлов, а неудачная финальная доставка
сохраняет прежний `backup.json`. Недоступный прежний receiver не запрещает подготовить
и проверить новый; после успешной замены прежний адрес сохраняется необязательным.

Монитор переносится после двух успешных текущих проверок нового primary, а не только
сохранённого состояния после debounce. Прежний монитор остаётся до проверки нового.
У свежего receiver может ещё не быть `monitor.json`: только отсутствие файла
разрешает первую настройку peer без rollback-конфига. Ошибка чтения, слишком большой
файл или некорректный JSON оставляют peer в `pending`; существующая конфигурация
сохраняется для отката. Это проверяют сценарии fresh receiver и optional previous
monitor в [тестах контроллера](test_reconcile.py).
Peer использует отдельный ключ только для forced-command
[проверенного heartbeat](heartbeat.py); cloud identity и API-ключ на exit не копируются.
Пара scoped private/public получает имя с отпечатком ключа. Public выводится из
private через `ssh-keygen -y`, а новый путь включается в конфиг монитора после
проверки SSH. Это предотвращает отказ OpenSSH из-за старого соседнего `.pub` при
замене private и сохраняет предыдущую активную пару при прерванной установке.
Регрессия проверяет реальную аутентификацию отдельным локальным OpenSSH daemon;
без `/usr/sbin/sshd` этот сценарий пропускается и должен быть проверен отдельно.
Vultr API используется только для существующих instance/firewall операции: сверяются
ID, IP и имя группы `ultra-operation-<id>`, затем добавляется недостающее правило
TCP 22 от конкретного peer IPv4 `/32`. Перенаправления API запрещены; 429 и временные
ошибки GET имеют ограниченные повторные попытки. Ошибка API оставляет peer в `pending`.
Копируются приватные данные существующего бота и согласованный профиль пробы; нового
бота, пользователей или квот контроллер не создаёт. Age identity остаётся у оператора.

Удалённые операции распознаются только по подтверждённому `deleted`/`cancelled`.
После готовности замены их мониторные units могут быть остановлены; архивы и ротация
не удаляются. Таймер не перекрывает собственные запуски, отдельный `flock` защищает
ручной запуск. Поздняя активация таймера запускает контроллер через 30 секунд (`OnActiveSec`),
даже если время `OnBootSec` уже прошло и предыдущая service выгружена systemd.
Приватный `status_file` содержит `ready`/`pending`/`error`, стадию ошибки
и идентификаторы ожидающих peer без секретов. Для чтения relay оператор должен отдельно
предоставить доступ только к этому файлу, сохранив приватность конфигурации и ключей.
Существующий API-ключ и cloud SSH identity могут принадлежать `ultra-relay`: root
читает их только по явно настроенной доверенной политике владельца, без смены
владельца или прав. Остальные конфиги, профиль и токен остаются root-only.
`status_group` разрешает чтение только диагностического файла группе `ultra-relay`;
его родительский каталог также должен быть доступен этой группе.
В резервное состояние включи приватный конфиг и стабильные `heartbeat_ed25519` и
`heartbeat_ed25519.pub` из `state_dir`. Весь каталог не включай: `state.json` меняется
каждый цикл, а топология восстанавливается из PostgreSQL. В `artifact_paths` включи
клиентский бинарник, `recovery.py`, `reconcile.py`, `monitor.py`, `heartbeat.py` и пять
шаблонов из `bundle_dir`: `ultra-recovery-prune.service`/`.timer`,
`ultra-monitor.service`/`.timer` и `ultra-monitor-probe.service`. Без шаблонов
восстановленный контроллер не сможет устанавливать receiver и монитор на новые exit.
Его собственные systemd units сохраняй в state-пакете.
Проверка: `python3 -m unittest discover -s deploy/recovery -p 'test_*.py'`.


## Штатное восстановление

Команда `ultra-install restore --config /secure/restore.json` устанавливает зависимости
на подготовленную Ubuntu VM, восстанавливает выбранное поколение и переключает
существующий ingress-узел. Полная [процедура восстановления и проверки age-ключа](RESTORE.md)
описывает fencing, продолжение после прерывания, приватные файлы и критерии готовности.
Примеры входных данных: [restore.json](restore.example.json) и [fencing](fence.example.json).
