# ultra

`ultra` — самоуправляемый сервис защищённого сетевого доступа. Клиент подключается
к узлу `bridge`, а тот применяет правила маршрутизации и передаёт поток на один из
узлов `exit`. Встроенное ядро [Xray-core](https://github.com/XTLS/Xray-core)
обслуживает VLESS, XHTTP/TLS и REALITY; управляющее состояние хранится в
PostgreSQL. Telegram-бот и Mini App дают пользователю подписку и показывают расход,
а администратору — управление доступами, узлами, квотами и диагностикой.

Проект рассчитан на небольшую частную инфраструктуру, где важны предсказуемое
поведение при отказах, сохранение учёта и воспроизводимое восстановление. Один
`ultra-relay` работает в роли `bridge` или `exit`; `ultra-install` строит и
применяет план установки; `ultra-bot` обслуживает Telegram и публичный HTTPS.

## Возможности

- Несколько `exit` с приоритетами, проверкой полной передачи данных и автоматическим
  выбором исправного разрешённого маршрута.
- Страна как предпочтение: при отказе или исчерпании остатка новые соединения
  переходят на другой разрешённый `exit`; возврат требует 60 секунд устойчивой
  исправности.
- Автономная работа `bridge` до 24 часов по подтверждённому локальному снимку при
  недоступной PostgreSQL. Перезапуск не продлевает срок.
- Транзакционное локальное состояние в bbolt: квотные резервы, неподтверждённые
  пакеты статистики и снимок управления сохраняются с единственным писателем.
- Идемпотентная доставка расхода в PostgreSQL. Потерянный ответ, повтор пакета,
  смена UUID, удаление пользователя и рестарт не возвращают потраченный объём.
- Общий пул Vultr для всех его `exit`, единая личная месячная квота, отдельный бюджет ручного выхода и конечный аварийный запас при
  временной недоступности API провайдера.
- Подписки Happ с профилями `Автоматически` и по странам, URI-представлением и
  полным JSON-представлением с XHTTP/TLS и резервным REALITY.
- Публичный HTTPS-кеш подписок до 24 часов. Telegram и PostgreSQL могут быть
  недоступны, а подтверждённые подписки продолжат выдаваться до исходного срока.
- Управляемые узлы Vultr: предложение цены, создание, установка, проверка,
  включение, замена и удаление из Mini App.
- Отдельный служебный доступ для внешних проверок с собственным владельцем учёта,
  лимитом и разрешённым набором HTTPS-целей.
- PostgreSQL на отдельном сервере, зашифрованные age-поколения состояния и
  отдельные неизменяемые артефакты бинарников.
- Полная автоматизация по схеме установки 2: DNS, TLS, мониторинг, копии,
  последовательное обновление, проверка готовности и совместимый откат.
- Управляемая смена домена с сохранением прежних адресов, UUID и токенов подписок.

Подробная карта компонентов и источников состояния: [архитектура](docs/architecture.md).

## Как проходит трафик

```text
Happ / локальный клиент
          |
          v
  bridge: публичные входы, авторизация, маршрутизация, квоты
          |
          +---- прямой маршрут по явным правилам
          |
          +---- защищённый канал ----> exit primary
          |
          +---- защищённый канал ----> exit independent

Telegram / Mini App ---> ultra-bot ---> loopback Admin API ---> PostgreSQL
                                      |
                                      +--> подтверждённый кеш подписок
```

PostgreSQL остаётся источником управляющих данных. Локальный bbolt-журнал на
`bridge` обеспечивает ограниченную автономность и сохраняет расход до его
подтверждения базой. Конфигурация ядра применяется одним сериализованным путём:
кандидат сначала проверяется, неудачный reload восстанавливает прежний вариант.
Изменение одной задержки не требует перезапуска ядра.

Admin API слушает loopback и требует Bearer-токен. Mini App отдельно проверяет
Telegram `initData` и права администратора. Публичные подписки защищены случайным
токеном; его хеш хранится в PostgreSQL, а зашифрованная копия — с версией keyring.

## Клиентские подписки

Пользователь получает одну HTTPS-ссылку и добавляет её в Happ. При обновлении
доступны `Автоматически` и профили опубликованных стран. UUID и токен ссылки не
меняются при замене `exit` или обновлении серверной части.

По умолчанию endpoint `/sub/<token>` сохраняет совместимое URI-представление.
`format=happ` явно запрашивает массив полных конфигураций Xray, а `format=uri` —
URI. Сервер может включить JSON по умолчанию для распознанного Happ; неизвестные
клиенты продолжают получать совместимый формат. Ответ содержит
`Vary: User-Agent`, а кеш разделяет форматы и транспорты.

Смешанный профиль Happ может содержать основной XHTTP/TLS и резервный REALITY.
Клиент проверяет доступность входов и выбирает рабочий; при отсутствии рабочего
варианта применяется завершающий `blackhole`. Публикация такого профиля требует
предварительной проверки на Android через Wi-Fi и мобильную сеть. Точный контракт,
preview-режим и матрица приёмки описаны в [документации Happ](docs/happ.md).

## Telegram-бот и Mini App

`ultra-bot` запускает HTTP независимо от подключения к Telegram. Обязательный
listener должен успешно открыться; затем long polling и очередь уведомлений
работают отдельными циклами. Временные ошибки Telegram повторяются с учётом
`retry_after` и задержкой с разбросом. Уведомление подтверждается только после
успешной отправки; при неоднозначном ответе возможен дубль.

Пользователь может:

- получить, обновить, отозвать или заменить ссылку подписки;
- открыть инструкцию Happ и QR-код;
- выбрать предпочтительную страну;
- видеть месячный расход и доступные остатки.

Администратор может:

- приглашать людей, включать и отключать доступ;
- управлять конфигурациями, UUID и квотами;
- видеть трафик по пользователям, владельцам учёта и `exit`;
- управлять серверами Vultr через подтверждаемые операции;
- проверять состояние `bridge`, `exit`, PostgreSQL, кеша, очередей и копий;
- назначать администраторов и проверять доставку уведомлений.

Регистрация закрыта и отделяет обычных пользователей от администраторов. См.
[регистрацию](docs/enrollment.md), [интеграцию Vultr](docs/vultr.md) и
[HTTPS-вход подписок](docs/subscription-ingress.md).

## Отказы и гарантии учёта

Подтверждённый снимок содержит пользователей, UUID, выходы, численные остатки и
срок действия. Если PostgreSQL недоступна, `bridge` продолжает проверять `exit`,
менять маршруты и учитывать передачу локально. Повреждённый, несовместимый или
просроченный снимок переводит пользовательские входы в закрытое состояние, сохраняя
защищённую диагностику.

Перед передачей через `exit` relay транзакционно резервирует до 256 КиБ на пару
«владелец—exit» для всех соединений и направлений. Неиспользованный остаток после
аварии считается потраченным. Каждые пять секунд измерения попадают в локальный
checkpoint; пакеты удаляются только после подтверждённого коммита PostgreSQL.
Очередь имеет конечный размер, поэтому невозможность надёжно записать локальное
состояние прекращает выдачу новых разрешений на передачу.

`account_id` не меняется при ротации UUID. Поздняя статистика удалённого пользователя
увеличивает общий расход узла, но не восстанавливает доступ. При возврате PostgreSQL
relay сначала доставляет накопленный расход, затем обновляет управляющий снимок.

Полный контракт и аварийные команды: [локальное состояние и учёт](docs/runtime-state.md).

## Установка и обновление

Для новых установок используйте схему 2. Канонические входы разделены:

- `install.config` в корне репозитория — локальный канонический файл топологии,
  доменов, публичного age recipient, бюджетов, путей и параметров развёртывания.
  Он исключён из Git и не содержит секретов: файл можно спокойно читать и
  актуализировать; секреты и содержимое приватных ключей хранятся отдельно;
- `.env` — токены, ключи API и другие секреты;
- каталог release — фиксированный набор артефактов и manifest с SHA-256.

Начальная подготовка:

```sh
cp install.config.example install.config
cp .env.sample .env
make release-dist

./ultra-install doctor --config install.config
./ultra-install apply --config install.config
./ultra-install status --config install.config
```

Для новой установки после `make release-dist` укажите в `install.config` абсолютный
путь к каталогу `dist` и точную версию из его `release-manifest.json`. Там же укажите
локальный `known_hosts` с ключами переустановленных серверов, сверенными с доверенным
источником провайдера; одного `ssh-keyscan` недостаточно. Для импорта `DATABASE_DUMP`
локально установите `pg_restore`. Полные предварительные требования и ограничения
восстановления описаны в [руководстве по установке](docs/automation.md#первоначальная-установка-и-принятие).

`doctor` проверяет локальные входы до изменений. `apply` готовит узлы и запускает
автоматизацию, а `status` возвращает готовность и безопасные коды причин без
секретов. `make deploy` предназначен для ручного upgrade/adoption, не для первой
установки на пустые серверы. Повторный запуск сохраняет существующие spec, UUID,
сертификатные pins и учёт. Старые конфигурации поддерживаются для обслуживания
прежней установки, но не подтверждают полный набор копий и внешнего мониторинга.

Ручная выкладка выполняется только из чистого tracked-дерева и committed `HEAD`:

```sh
ULTRA_OPERATOR_IDENTITY=/secure/operator/ssh-key \
ULTRA_OPERATOR_KNOWN_HOSTS=/secure/operator/known_hosts make deploy
```

`install.config` задаёт bridge и статические узлы; скрипт берёт первый static exit
как SSH jump host. `ULTRA_OPERATOR_IDENTITY` и `ULTRA_OPERATOR_KNOWN_HOSTS` — пути
к локальным файлам оператора: выделенному SSH-ключу с правами 0600 и файлу с
проверенными host-key pins. Соединение использует строгую проверку ключей и не
читает пользовательский `~/.ssh/config`. Эти файлы остаются локальными.
Для запуска из отдельного worktree передайте канонический файл параметром
`INSTALL_CONFIG=/absolute/path/to/install.config`; канонический файл храните с
правами 0600.
`ULTRA_OPERATOR_INVENTORY` не требуется; он остаётся совместимым способом
продолжить adoption по существующему failed-operation артефакту. Создавать и
поддерживать отдельный inventory вручную не нужно.

Скрипт собирает и проверяет release для точного `HEAD`, затем передаёт на bridge
комплект и обновлённый канонический `install.config` в
`/var/lib/ultra-ansible/operator-inputs/manual-<SHA>-<attempt>/release`. Файл `.env` и другие
секреты не копируются. Успешная команда выполняет `doctor`, затем `upgrade` и
`status`; в режиме adoption вместо upgrade запускаются read-only сравнение,
`apply` и `status`. Теги, публикацию GitHub Release и фоновые обновления команда
не создаёт.

Для первой выкладки поверх уже работающего runtime включайте adoption только явно:

```sh
ADOPT=1 ULTRA_OPERATOR_IDENTITY=/secure/operator/ssh-key \
ULTRA_OPERATOR_KNOWN_HOSTS=/secure/operator/known_hosts make deploy
```

Это выполняет `doctor`, `adopt --check --adopt-runtime --bridge-native`,
`apply --adopt-runtime --bridge-native` и `status`. Без `ADOPT=1` принятие
не запускается. Ошибка подготовки или read-only сравнения до отправки mutator
восстанавливает предыдущий локальный config и удаляет журнал. После отправки
изменяющей команды при ошибке config и приватный журнал сохраняются: задание на
bridge может продолжаться. `ultra-install status` показывает готовность сервисов,
но не доказывает завершение старого удалённого задания и не снимает блокировку
выкладки. Для dispatched `upgrade` есть отдельный поддерживаемый `--forward-only`
с явным preflight. Для dispatched `adoption_apply` текущий wrapper блокирует retry:
до появления протокола fencing всех источников dispatch и host-bound подтверждения
drain на frozen target set не меняйте config, не удаляйте журнал и не запускайте
другой commit.
Подробности и ограничения: [инструкция по автоматизации](docs/automation.md).

## DNS, TLS и собственный домен

Схема 2 умеет управлять двумя A-записями в уже созданной зоне Vultr: служебным
HTTPS-адресом подписок и публичным адресом `bridge`. API-доступ DNS отделён от
compute-доступа. Операция не изменяет apex, не удаляет посторонние записи и принимает
существующую запись только при наличии собственной квитанции. Потерянный ответ,
drift и дубликаты обрабатываются консервативно.

Nginx разделяет HTTPS на стандартном порту по имени: один virtual host передаёт
подписки локальному TLS listener бота, второй обслуживает XHTTP. Сертификаты и
ACME webroot независимы; продление выполняет graceful reload Nginx.

`domain-cutover` предназначен для работающей установки. Он создаёт новые aliases,
проверяет старую и новую подписки и тестовую передачу, делает свежую копию и только
затем меняет publication metadata. Существующие VPN UUID и параметры подключения
сохраняются; прежние XHTTP и subscription listeners при необходимости сохраняются
как принадлежащие Ultra aliases для совместимости и отката. Операция имеет журнал,
продолжение после прерывания и возврат к прежней публикации при ошибке. Команды
backend/public cutover, порядок действий и клиентская приёмка описаны в
[инструкции HTTPS-входа](docs/subscription-ingress.md#перенос-backend-и-публичных-имён).

TLS внутреннего канала и правила сертификатов: [deploy/TLS.md](deploy/TLS.md).

## Отдельная БД, копии и мониторинг

PostgreSQL 16 размещается на отдельном сервере. В `install.config` задаются его
`DATABASE_IP` и `DATABASE_SSH_KEY`; Ansible создаёт отсутствующие роль и
БД, а relay применяет миграции при запуске. Bridge подключается через закреплённый
SSH-туннель `127.0.0.1:25432` → DB `127.0.0.1:5432`.
Физические реплики и PostgreSQL на VPN-хостах не поддерживаются.

Каждые две минуты recovery timer создаёт согласованный `pg_dump -Fc`, собирает
явно перечисленные настройки и ключи, шифрует пакет публичным age-ключом оператора
и доставляет его на обязательные `exit`. Бинарники и geo-assets хранятся отдельным
зашифрованным артефактом по версии. Незавершённая доставка не заменяет последнее
пригодное поколение; получатель проверяет имя, размер, SHA-256 и выполняет ротацию.

Приватный age identity не размещается на серверах. Его нужно хранить у оператора и
периодически доказывать пригодность расшифрованием заново извлечённого поколения.
Статус различает свежесть копии и независимость провайдера: копия на другом узле
того же провайдера остаётся полезной, но не считается независимой.

Внешний монитор использует отдельный `service_access`, проверяет полный HTTPS-путь
через разрешённый `exit` и отправляет события через существующего Telegram-бота.
Его локальная очередь переживает недоступность Telegram и перезапуск процесса.

Инструкции: [отдельная БД](docs/replication.md),
[резервное копирование и восстановление](deploy/recovery/README.md),
[перенос bridge](docs/bridge-migration.md).

## Операторский доступ и восстановление

Автоматизация устанавливает постоянные инструменты в `/opt/ultra-recovery`,
конфигурацию — в `/etc/ultra-recovery`, состояние — в
`/var/lib/ultra-automation`. Таймеры и восстановление не зависят от процессов или
скриптов в `/tmp`. SSH использует заранее проверенный `known_hosts`.

При потере `bridge` оператор:

1. изолирует прежний primary;
2. извлекает подходящее зашифрованное поколение и соответствующий артефакт;
3. проверяет оба пакета на доверенной машине с age identity;
4. восстанавливает PostgreSQL 16, роли, файлы, systemd, Nginx и ACME webroot;
5. выполняет smoke-проверку до публикации;
6. переключает DNS только после подтверждения единственного primary.

Изолированное учение использует отдельную VM и тестовую сеть, чтобы восстановленные
worker не обращались к рабочим узлам, Telegram или API провайдера. Инструкция и
ограничения fencing находятся в [recovery runbook](deploy/recovery/README.md).

## Сборка и проверки

Требуется версия Go из `go.mod`.

```sh
make build
make build-install
make build-bot
make test
make vet
make lint
make test-ui
make harness-check
```

`make test` без `DATABASE_URL` не запускает DB-интеграцию. Для неё нужна явно
выделенная PostgreSQL 16: пакет `db` применяет миграции. Полная матрица включает
race, сборки обеих архитектур, настоящий Nginx, проверку восстановления и
нагрузочный сценарий с TCP/UDP во время копирования и смены маршрута. См.
[руководство разработки](docs/development.md).

## Диагностика

`GET /v1/health` защищённого Admin API разделяет живость процесса и готовность
функций. В нём доступны состояние PostgreSQL и Telegram, возраст runtime-снимка,
активный `exit`, причины выбора маршрута, очередь статистики, reload ядра,
свежесть копий. Публичный `/healthz` бота сообщает только живость HTTP.

```sh
./ultra-install status --config install.config
make verify-relay
make verify-miniapp
make relay-logs SINCE_RESTART=1
```

`make verify-relay` запускается явно после установки и по умолчанию проверяет внешний
IP через `https://api.ipify.org`. При необходимости задайте другой HTTPS-адрес через
`VERIFY_IP_URL` в окружении команды. Локальный SOCKS по умолчанию слушает порт 10808.
Чтобы изменить порт, передайте значение при вызове,
например `make verify-relay VERIFY_SOCKS_PORT=10809`; одноимённое поле в
`install.config` не используется этим скриптом.
`VERIFY_AFTER_INSTALL` и `VERIFY_FAIL_LOG_LINES` не запускают проверки в текущем
Ansible-пути установки, поэтому добавлять их в конфигурацию не требуется.

Логи не должны содержать токены подписок, ключи провайдеров, приватный age identity,
DSN или ответы внешнего API целиком. Неизвестные ошибки облака сохраняются как
ограниченные коды этапа с HTTP-статусом.

## Границы системы

- Один `bridge` и его IP остаются общей точкой отказа. Автоматизация сокращает
  восстановление, но не создаёт второй независимый вход.
- PostgreSQL размещается на одном отдельном сервере. Резервные копии служат
  восстановлению; автоматического переключения БД нет.
- Автономный срок ограничен 24 часами от последнего полного подтверждения.
- Строгие внешние белые списки и доступность новой VM из каждой пользовательской
  сети не проверяются автоматически.
- Переключение нового соединения не сохраняет уже установленную TCP-сессию.
- Проверка сайтов на Android подтверждает пользовательский TCP-сценарий, но сама
  по себе не доказывает обработку всего UDP/DNS-трафика устройства.
- Расход, показанный ядром, может отличаться от биллинга провайдера; бюджет поэтому
  сохраняет резерв.
