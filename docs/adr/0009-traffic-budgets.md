# 0009 — Учёт выходов и адаптивные бюджеты трафика

## Статус

accepted

## Дата

2026-09-08

## Контекст

Профили одной подписки могут выходить через разные узлы; split routing также
использует прямой выход с bridge. Сумма по пользователю не показывает, какой узел
израсходовал трафик. Бюджет Vultr ограничен, а неактивные пользователи не должны
резервировать равную долю. Основной резерв при исчерпании бюджета — Амстердам.

## Решение

Считать полезные байты на фактически выбранном outbound Xray, суммируя UUID
профилей на владельца. Сохранять дневные итоги по пользователю и outbound без
адресов назначения. Старую неатрибутированную статистику показывать отдельно.

Хранить бюджет каждого ограниченного exit. Для Vultr читать начисленные кредиты
аккаунта и исходящий трафик экземпляра; оставлять 20% запаса. Общий остаток аккаунта
распределять между управляемыми узлами пропорционально их бюджетам. Месячный тариф
не трактовать как уже начисленный трафик. Для основного узла бюджет задаётся вручную.

Адаптивная дневная квота зависит от остатка месяца и использования предыдущих семи
дней: вес — квадратный корень расхода. Начальный доступ — до 2 ГиБ в пределах пула;
он не резервируется за неактивными аккаунтами. Это потолок возможности использования,
а не гарантированная личная доля. Общий бюджет имеет приоритет. Для Амстердама нет
индивидуального деления; действует общий защитный предел.

После исчерпания квоты направлять затронутые профили на явно заданный основной
резерв. Если он недоступен или исчерпан, блокировать предназначенный для туннеля
трафик, сохраняя правила direct. Ошибка или устаревание данных Vultr исключает
управляемый выход. Новые пользователи не обходят лимиты до первого расчёта.

## Рассмотренные альтернативы

- Равные доли всех зарегистрированных пользователей: простаивают у неактивных.
- Только метрики хостинга: нет привязки к VPN-пользователю, данные запаздывают.
- Только локальные байты: не учитывают накладные расходы и другое использование аккаунта.
- Точное ограничение каждого байта: требует отдельного механизма в тракте передачи.

## Последствия

Сбор трафика и применение квот периодические: допускается превышение между циклами,
а при сбое БД часть дельт может потеряться. Защитный запас уменьшает риск, но не
гарантирует отсутствие счёта за перерасход. API Vultr проверяется каждые пять минут,
данные старше 15 минут не используются; квоты пересчитываются каждые 30 секунд.
Применение меняет общее ядро и может прервать соединения. При ошибке применяется
повтор, интерфейс отличает ожидающий применения лимит от подтверждённого.

Доступность устройства нельзя выводить из отсутствия байтов; показывается последнее
наблюдение трафика. Квоты и история принадлежат владельцу и сохраняются при ротации UUID.
