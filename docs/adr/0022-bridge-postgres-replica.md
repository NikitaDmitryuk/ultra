# 0022 — Реплика PostgreSQL на bridge

## Статус

accepted

## Дата

2026-10-16

## Контекст

Отдельный PostgreSQL-сервер сохраняет независимость базы от VPN-узлов, но при
его отказе только логический dump требует восстановления перед возобновлением
работы. Требуется постоянно обновляемая копия на главном VPN-сервере `bridge`.

## Решение

Dedicated `database` остаётся единственным primary и центром записи.
`bridge` запускает асинхронную физическую streaming-реплику PostgreSQL 16 в
отдельном кластере; `exit` PostgreSQL не запускает. Приложение подключается к
primary через существующий bridge SSH-туннель. Реплика не становится целью
прикладного DSN, не продвигается автоматически и не заменяет зашифрованный
логический backup. Неожиданный непустой каталог реплики блокирует её повторную
инициализацию. Promotion требует отдельного решения о fencing старого primary.

## Рассмотренные альтернативы

Единственный primary без реплики оставляет восстановление зависимым от dump.
Автоматический failover не выбран без надёжного fencing и согласованного
переключения writer endpoint. Размещение основной БД на bridge смешало бы
жизненный цикл VPN и primary, поэтому не выбрано.

## Последствия

Bridge получает дополнительную нагрузку по диску, памяти и WAL replay. Реплика
может отставать; потеря нужного WAL потребует безопасной повторной базовой копии.
Копии остаются нужны для независимого восстановления. При отказе primary
автоматического переключения нет. Повтор bootstrap сохраняет идентичность
primary и безопасно проверяет состояние standby.
