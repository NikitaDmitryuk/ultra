# Архитектурные решения

ADR фиксирует долгосрочный выбор границ компонентов, данных, доверия, внешних контрактов и эксплуатации. Текущее устройство описывает [архитектура](../architecture.md), процедуры — тематические инструкции.

## Правила отбора

- Решение должно быть полезно после завершения текущей задачи и иметь проверяемые источники.
- Не записывать результаты отдельных запусков, текущие IP и тарифы, временные обходы, пробные параметры, журналы расследований и неподтверждённые причины сбоев.
- Эксперимент становится основанием ADR только после принятия долгосрочного решения; его оперативные настройки остаются вне ADR.
- Сохранять известную аргументацию. Изменение решения оформлять новым ADR; неизвестные исторические мотивы не придумывать.

## Формат и жизненный цикл

Использовать [шаблон](template.md), имя `NNNN-short-title.md` и следующий свободный номер. Номера не переиспользуются. Разделы шаблона и дата `YYYY-MM-DD` обязательны.

- `proposed` — ещё не принято владельцем.
- `accepted` — согласовано; этот статус сам по себе не подтверждает завершение реализации.
- `superseded` — заменено: обязательна ссылка на новый ADR в разделе «Заменено».
- `deprecated` — не действует и замены нет; причина описана в последствиях.

Структуру и ссылки проверяет `make harness-check`; обоснованность и устойчивость содержания проверяет ревью.
