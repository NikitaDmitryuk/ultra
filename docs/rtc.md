# Аварийный RTC-доступ

RTC — очень медленный резервный TCP-вход через сервис конференций. Клиент подключается
к комнате, серверный транспорт передаёт полезные данные локальному gateway на bridge,
дальше действуют существующие маршруты, выбор exit и квоты. Адрес exit не включается
в клиентский профиль. Прикладной UDP не поддерживается.

## Опциональный модуль

`rtc_service.enabled` в spec управляет всем модулем. По умолчанию `false`:
страница и статистика скрыты, API и экспорт недоступны, приватные инструкции не нужны.
Установщик принимает `RTC_SERVICE_ENABLED=1` в приватном `install.config` и переносит
значение в spec. При выключении установщик останавливает RTC-службы; supervisor также
останавливает дочерние процессы через 60 секунд без управляющей синхронизации.
Настройки в БД и статистика сохраняются.

Для включения нужны `RTC_CONTENT_FILE`, `RTC_SUPERVISOR_BINARY`,
`RTC_TRANSPORT_BINARY`, `RTC_TRANSPORT_SHA256` и `RTC_GATEWAY_PORT` (по умолчанию 12001).
Соберите supervisor командой `GOOS=linux GOARCH=amd64 go build -o /private/build/ultra-rtc-supervisor-linux-amd64 ./cmd/ultra-rtc-supervisor`.
Транспорт собирается [закреплённым скриптом](../tools/build-olcrtc.sh); mutable latest не используется.
Пути в install-плане относятся к машине, с которой запускается установщик, включая `apply-remote`.

Приватный JSON содержит:

- `guide.steps`: массив текстовых шагов; `guide.warning`: предупреждение об аккаунте.
- `guide.links`: объекты `label`, `url` с HTTPS-ссылками.
- `guide.import_template`: ссылка импорта с единственным маркером `{url}`.
- `room_rules`: объекты `host`, `path_pattern`, `provider`; регулярное выражение пути
  содержит одну группу с ID комнаты и должно совпадать с полным путём.
- `probe_url`: фиксированный HTTPS-адрес, возвращающий 65536 байт со статусом 200.
- `bootstrap_dns`: DNS IP:53, доступный с bridge.
- `max_accesses`: от 1 до 10, по умолчанию 10.

Файл хранится вне Git с правами 0600, на bridge — root:ultra-relay 0640.
Названия и ссылки внешних сервисов, инструкции и реальные идентификаторы не копируются
в публичные инструкции, исходники интерфейса или тестовые фикстуры.

## Пользовательский сценарий

Вкладка «Белые списки» доступна активным зарегистрированным пользователям.
Пользователь создаёт личную пустую комнату по приватной инструкции и вставляет ссылку.
Владение аккаунтом по одной ссылке проверить нельзя; cookies и пароли не запрашиваются.
Один пользователь получает один доступ, одна комната не может использоваться дважды.
Создаваемые и восстанавливаемые доступы занимают слот. Блокировка владельца отзывает
доступ и освобождает слот; временное применение выбранного маршрута не удаляет настройки.

Создание асинхронное. «Проверка пройдена» означает передачу проверочных данных через
комнату и персональный gateway, а не доказанную доступность при ограничениях оператора.
Сервер остаётся в комнате, даже если пользователь отключил приложение.
Повторная отправка той же ссылки идемпотентна. Замена или пересоздание сразу отзывает
прежние ключи; после проверки нужно обновить профиль. Отключение закрывает соединения
и завершает серверное участие. Старые настройки не восстанавливаются при ошибке замены.

Подписка использует существующий токен и `?format=olcrtc`. Сохраните профиль заранее:
публичный сервер подписки может быть недоступен при ограничениях. Кнопка «Добавить в приложение» открывает HTTPS-страницу в браузере, где отдельное
нажатие передаёт подписку установленному клиенту. Шаблон из приватного конфига
использует действие `add` или `add-subscription` и параметр `url`. Ссылка передаётся
во фрагменте и сразу удаляется из истории; страница не загружает сторонние ресурсы.
Копирование профиля позволяет вставить настройки через импорт из буфера обмена
без обращения приложения к подписке. После замены доступа такой профиль нужно
импортировать заново. Счётчик в личном и административном кабинете называется
«Трафик белых списков». Ответы имеют
`Cache-Control: no-store`; секреты не сохраняются в браузерном хранилище.

## Runtime и учёт

[Gateway и reconciler](../internal/rtcingress/service.go) управляют доступами без изменения
общего Xray JSON. Gateway передаёт доверенную личность владельца в `core.Dial`.
Правило приватных адресов применяется перед split routing; DNS использует `IPOnDemand`.
Это не исключает DNS rebinding при повторном разрешении имени на выходе.

[Supervisor](../internal/rtcsupervisor/supervisor.go) работает отдельным пользователем,
принимает команды через Unix-сокет с проверкой UID и не наследует DSN или Admin API token.
Дочерние процессы получают минимальное окружение, их stdout/stderr не сохраняются.
Проверка комнаты ограничена 120 секундами, выполняется одна за раз, временный клиент
завершается после неё. Ограничения службы: 2 CPU, 2 ГиБ; gateway — 64 TCP-потока на доступ.

Комнаты и ключи в PostgreSQL зашифрованы AEAD с отдельным контекстом RTC; ключ расшифрования
находится вне БД. Установщик создаёт отдельный файл `/etc/ultra-rtc/keys.json` (ultra-relay, 0600);
его необходимо сохранять вместе с защищённой резервной копией БД для восстановления.
Уникальность комнаты проверяется по HMAC с отдельным зашифрованным ключом.
Состояние связано с поколением доступа: ответ старой операции не публикует старые ключи.

Полезные байты на входе сохраняются отдельно в `rtc_ingress_hourly` и показываются
справочно, без повторного списания из квоты. Учёт выхода не меняется. Период записи —
минута; повторная запись накопительного значения идемпотентна. Аварийное завершение
может потерять несохранённый интервал. История начинается с внедрения нового учёта.

Решение: [ADR 0013](adr/0013-rtc-ingress.md). Проверки транспорта:
[тест маршрутизации](../internal/rtcingress/routing_test.go),
[изоляция и счётчики](../internal/rtcingress/gateway_test.go),
[БД](../internal/db/repo_rtc_test.go).

## Возврат к версии без RTC

Миграция 022 добавляет отдельные таблицы и не меняет основные. При возврате к версии,
знающей миграции 001–021, сохраняйте RTC-таблицы и запись 022: мигратор проверяет
только известные ему версии. Перед заменой бинарников сделайте резервную копию БД
и приватных конфигураций, остановите и отключите RTC-службы. Сначала запустите relay,
проверьте готовность обычного транспорта, затем запускайте бота.

Перед последующим обновлением сверяйте номера и содержание миграций: если другая ветка
использует номер 022 для иной схемы, имеющаяся запись приведёт к пропуску её миграции.
Такой конфликт требует отдельного согласования схемы; удалять запись 022 вслепую нельзя.
Приватные RTC-конфигурации и ключи сохраняйте вне Git для возможного восстановления.
