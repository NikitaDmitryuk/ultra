# PostgreSQL primary, реплика и резервные копии

PostgreSQL 16 primary размещается на отдельном сервере `database`; `bridge`
поддерживает его асинхронную физическую streaming-реплику. `exit` не запускает
PostgreSQL. Прикладной DSN остаётся направлен через SSH-туннель на primary:
реплика read-only и не участвует в автоматическом переключении или promotion.
Логические зашифрованные копии сохраняются как отдельный механизм восстановления.

## Текущий статус standby

Mini App получает `/api/cloud/replicas` через административный relay API
`/v1/cloud/replicas`. Каждый запрос читает состояние физического slot
`ultra_bridge` и соответствующего WAL sender на primary; карточка обновляется
каждые 10 секунд независимо от операций Vultr. Это одна standby на bridge,
не список exit и не таблица `node_replication`.

Диагностика primary использует admin-only `/api/database` и relay endpoint
`/v1/database`. `primary_host` берётся из deployment metadata (`DATABASE_IP`),
а не выводится из адреса пула: тот может быть `127.0.0.1` на конце SSH-туннеля.
`reachable` и `observed_role` показывают результат SQL-проверки через пул
приложения; это не отдельная проверка SSH-доступности физического хоста.
Старые runtime spec без `primary_host` возвращают `null`, пока metadata не
появится при следующем render/runtime projection.

Ansible PostgreSQL bootstrap устанавливает в прикладной БД функцию
`ultra_monitor.bridge_replication_status()`. Схема и функция принадлежат
`postgres`; `PUBLIC` лишён доступа. Прикладная роль получает только `USAGE`
схемы и `EXECUTE` функции с фиксированным `search_path=pg_catalog`.
Функция не принимает аргументов и не раскрывает адреса, connection strings
или сведения других replication clients; `pg_monitor` приложению не выдаётся.
Привилегированная установка принадлежит Ansible, а не прикладным миграциям.
Схема `ultra_monitor` — управляемая инфраструктура: logical dump исключает её
через `--exclude-schema=ultra_monitor`, чтобы restore с `--no-owner --no-acl`
не менял владельца SECURITY DEFINER и не открывал его `PUBLIC`.
Оба bootstrap playbook устанавливают монитор в `post_tasks` после возможного
`database_import`, сохраняя проверку пустой целевой БД; роль `restore_database`
устанавливает его после подтверждённого восстановления. При ручном logical dump
используйте то же исключение; состояние монитора не переносится из архива.

Ответ содержит одну запись `id=bridge`, `source=primary`, `state`,
`replay_lag_bytes` (nullable) и `checked_at` в UTC. `streaming` означает
активный sender с известным replay LSN; `syncing` — sender ещё не streaming
или replay LSN ещё неизвестен; `lagging` — отставание replay больше 16 MiB.
Без sender для точного slot состояние `disconnected`; без самого slot —
`unknown`. Отставание измеряется в WAL-байтах: отсутствие новых транзакций
не считается неисправностью. Это наблюдение с primary, оно само по себе
не доказывает локальную исправность диска или отсутствие ручного promotion
на отключённом bridge. Потеря соединения определяется после обнаружения
разрыва PostgreSQL, а не мгновенно.

Ошибка БД или отсутствие установленной функции дают HTTP 503 и сообщение
о временной недоступности наблюдения; UI не сохраняет прежнее зелёное состояние.
После обновления старой установки функцию создаёт повтор PostgreSQL bootstrap.
Локальная регрессия `python3 scripts/test-ansible-postgres-monitor.py`
использует одноразовый Docker `postgres:16`, проверяет streaming, replay,
отставание, отключение, повтор установки SQL и ограничения прав.

## Установка

В приватном `install.config` адреса и операторские ключи задаются только парами:
`BRIDGE_IP` / `BRIDGE_SSH_KEY`, `MAIN_EXIT_IP` / `MAIN_EXIT_SSH_KEY`,
`DATABASE_IP` / `DATABASE_SSH_KEY`. Адрес БД отличается от VPN-хостов.
`SSH_USER` задаёт общего SSH-пользователя; `DB_NAME` и `DB_USER` — имена БД
и прикладной роли. Старые ключи `BRIDGE`, `EXIT`, `DB_HOST`, `IDENTITY`
и параметры репликации отклоняются.

Ansible устанавливает PostgreSQL на database и bridge, создаёт отсутствующие
прикладную и ограниченную роль репликации на primary и настраивает loopback-only
listener. Для новой роли явно используется SCRAM. Если прикладной DSN взят из
сохранённого bridge spec или `DB_CREDENTIALS_FILE`, он является источником истины:
при неудачной проверке login bootstrap выставляет этому паролю SCRAM verifier и
повторяет вход. Для существующей базы задайте `DB_CREDENTIALS_FILE` с проверенным
прежним DSN. Вместе с приложением пересогласуется выделенная роль репликации,
пароль которой детерминированно выводится из прикладного. Когда DSN создан заново,
существующая роль по умолчанию не меняется;
для осознанного восстановления выставьте `DB_REPAIR_APP_CREDENTIALS=true` в
приватном `install.config`. Переключатель меняет пароль роли только после провала
login, до активации bridge; удалите его после успешной выкладки. Эта процедура не
пересоздаёт базу и не затрагивает таблицы. Без доверенного прежнего DSN или явного
переключателя bootstrap останавливается с подсказкой, как продолжить.
Между bridge и БД
работает `ultra-db-tunnel.service`: приложение подключается к
`127.0.0.1:25432`, SSH пересылает соединения на DB `127.0.0.1:5432`.
Этот же туннель переносит replication protocol; отдельный кластер standby слушает
только loopback bridge и не меняет прикладной endpoint. Служебный ключ туннеля
создаётся на bridge; сервер принимает его только для этого forwarding. SSH host
keys закреплены в проверенном known_hosts. Операторский приватный ключ не переносится на bridge.

Миграции выполняет relay при запуске; ORM не меняет схему самостоятельно.
Повторная установка сохраняет DSN и пароль из существующего spec и требует
уже настроенный туннель. Перенос данных со старого размещения выполняется
явно до повторной установки. Для нового bridge с сохранённой БД задайте
`REUSE_BRIDGE_SPEC=false` и `DB_CREDENTIALS_FILE`: путь к приватному файлу прежнего
`spec.json` с DSN (например, из проверенной расшифрованной копии). Файл должен быть
обычным файлом с правами 0600; DSN должен совпадать с DB_NAME/DB_USER и endpoint
туннеля. Его пароль используется повторно и не попадает в `install.config`.
Без этого входа новый пароль предназначен только для новой БД; Ansible не меняет
существующую роль автоматически и проверяет прикладной login до активации bridge.


## Копии и восстановление

Зашифрованные age-поколения включают логический `pg_dump`, управляющее состояние,
сертификаты, служебный ключ и настройки DB-туннеля. Копии доставляются на
независимые доступные узлы. Для dump используются прикладные учётные данные
через временный `PGPASSFILE`; пароль не включается в аргументы процесса.

Реплика отстаёт асинхронно и может потребовать повторной базовой копии после
потери удерживаемого WAL. Неожиданный непустой каталог standby блокирует
переинициализацию. Реплика не заменяет backup и не продвигается автоматически:
отказ primary требует отдельной процедуры fencing и ручного переключения.

Аварийное восстановление использует отдельный `database_target` в приватном
restore JSON. В нём задаются операторские SSH endpoint, identity и known_hosts;
ключ остаётся на операторской машине. Дамп можно восстановить только в пустую
БД на отдельном хосте. Текущий CLI restore устанавливает туннель и активирует
relay, но не создаёт и не проверяет физическую standby на bridge. Такое
восстановление возвращает сервис, но ещё не восстанавливает полную штатную
топологию PostgreSQL; учитывайте это при оценке готовности после аварии.
PostgreSQL standby не содержит независимой копии внешних ключей и конфигурации
relay. Инструкции: [recovery](../deploy/recovery/README.md).

Управляемое перемещение primary на bridge, promotion, автоматический failover и
произвольный выбор replica-host не поддерживаются. Перенос bridge не должен
восстанавливать старый дамп поверх общей БД. Старые файлы незавершённых операций
требуют отдельного разбора до изменения канонического `install.config`; наличие
дампа не разрешает обход журнала.

### Начальная загрузка данных

Для чистого DB-хоста `DATABASE_DUMP` задаёт путь к локальному приватному
custom-format архиву `pg_dump`. Нужен локальный `pg_restore`: установщик проверяет
архив до удалённых изменений и закрепляет SHA-256 в плане и запросе операции.
Ansible передаёт архив напрямую DB-хосту, проверяет пустоту/отсутствие БД,
создаёт прикладную роль и БД, затем импортирует одной транзакцией. Действующую
непустую БД импорт не перезаписывает; повтор принимает только квитанцию,
связанную с архивом, идентификатором кластера и OID БД. Временный upload удаляется.
Поле предназначено для свежего bootstrap с `REUSE_BRIDGE_SPEC=false`; без него
создаётся чистая БД. Relay применяет миграции перед обслуживанием запросов.

Перед активацией свежего bridge установщик согласует импортированные exit с
проверенными новыми exit по точному IP и порту. Для каждого настроенного exit
должна существовать ровно одна включённая строка: отсутствие, выключенная строка
или неоднозначность блокируют активацию. В одной транзакции меняются только
`tunnel_uuid` и TLS pin (для CA-аутентификации прежний leaf pin очищается).
ID, enabled, membership, бюджеты, учёт трафика, пользователи и остальные exit
сохраняются. Квитанция импорта проверяется по архиву, кластеру и OID БД;
в БД сохраняется привязка к этим данным, маршрутам, TLS policy и проверенным pins.
Точный повтор проверяет сохранённый результат. Новый fresh bootstrap может
обновить UUID и pins, если каждый endpoint по-прежнему соответствует той же
строке `exit_nodes`; marker атомарно обновляется в той же транзакции. Изменение
набора endpoint или соответствия строк блокирует активацию. При неизменной
привязке tampering UUID/pins также блокируется. Согласование требует таблицу `exit_nodes`
с полем `pinned_peer_cert_sha256`; несовместимый старый дамп блокирует активацию
и требует отдельной миграции. Без явного импорта обычный bootstrap непустую БД
не меняет.

Служебный ключ bridge → exit хранится отдельно от операторских ключей:
`/etc/ultra-fleet` принадлежит root, имеет группу ultra-relay и права 0750;
сам ключ принадлежит ultra-relay с правами 0600. Резервная копия сохраняет
ключ и публичную часть, а восстановление возвращает права родительского каталога.

После аварийного восстановления bridge доступ к управляемым exit возобновляется
до запуска relay: из восстановленной БД читаются готовые включённые узлы и их
TCP-порты. Проверяются принадлежность provider firewall, закреплённые SSH host
keys и служебный ключ; новому bridge разрешаются TCP/22 и фактический порт
туннеля в provider firewall и активном UFW. Ошибка блокирует запуск relay.
Для статических exit UFW обновляется по закреплённому SSH; firewall провайдера
остаётся операторским. Недоступность статического exit блокирует активацию с
требованием проверить provider firewall и SSH, затем повторить восстановление. Этот шаг
не создаёт реплик и не меняет данные БД.
