# Копии PostgreSQL для ручного восстановления

Основная БД остаётся на bridge. На доступных exit с достаточным местом worker
поддерживает асинхронные физические копии PostgreSQL. Они нужны для восстановления;
бот и relay не переключают запись на них автоматически. Решение:
[ADR 0008](adr/0008-database-recovery.md).

## Установка и ограничения

Локальный установщик сохраняет возможность настройки обычных узлов. Его
`SetupReplicaPostgres` разрешает SSH-доступ выделенному ключу bridge и настраивает
worker; успешная авторизация ещё не означает завершение копирования. Для нескольких
exit установочный план подключает каждый узел. Уже установленные узлы должны разрешать
тот же публичный ключ в SSH. Веб-интерфейс управляет созданием серверов только через Vultr.

`ULTRA_REPLICATION_KEY_FILE` — отдельный файл с полями `user`, `password`, `port`.
Пароль — случайные 32 байта в hex. Локальный установщик создаёт выделенную роль
`ultra_recovery` с `LOGIN`, `REPLICATION` и `pg_monitor`, не меняя прикладной пароль.
Ключ SSH задаётся `ULTRA_VULTR_SSH_KEY_FILE` и используется также без интеграции Vultr.
Настройки находятся в systemd drop-in `recovery.conf`; после первоначальной настройки
их подхватывает следующий запуск relay. При необходимости рестарта PostgreSQL
установщик сообщает об этом; такой рестарт следует планировать отдельно.

Соединение идёт через SSH reverse forwarding между loopback-портами. PostgreSQL
не открывается для репликации в интернет. На exit отдельный кластер:

- данные `/var/lib/ultra-postgres-replica/data`;
- настройки `/etc/ultra-postgres-replica/`;
- unit `ultra-postgres-replica.service`, локальный порт 5433;
- слот основной БД `ultra_<ID узла без дефисов>`.

Стандартный кластер PostgreSQL не удаляется. Несовпадающая архитектура или версия,
чужой каталог данных и отсутствие `standby.signal` у существующей копии блокируют
перезапись. Внешние tablespace требуют отдельного проекта восстановления и не
поддерживаются автоматическим bootstrap.

Перед копированием свободное место должно быть не меньше `max(5 ГБ, 2 × размер
кластера + 2 ГБ)`. При остатке менее 1 ГБ replica останавливается. Недостаток места
не отключает VPN узла. Лимит `max_slot_wal_keep_size=1GB` ограничивает удержание WAL
отстающими копиями; после длительного разрыва слот может стать непригодным и
потребовать ручного пересоздания копии. Асинхронность допускает потерю последних
транзакций при аварии. Реплика также повторяет ошибочные удаления; сохраняйте
отдельные резервные копии.

## Проверка и восстановление

«Сервис → Серверы» показывает состояние и запас диска каждой копии. `streaming`
означает поток репликации с подтверждённым отставанием не более 16 МиБ; `syncing`
ещё не подтверждает готовность. Проверяйте свежесть отметки времени. Нулевое
отставание по байтам не заменяет пробное восстановление.

Перед ручным восстановлением:

1. Изолируйте прежний primary от записи и остановите его relay/бота/worker.
   Нельзя одновременно оставлять два независимых primary.
2. Выберите свежую копию, проверьте `pg_is_in_recovery()`, состояние replay и
   целостность нужных данных. Сохраните копию каталога перед изменением роли.
3. На выбранном узле выполните `pg_ctl promote` от postgres для **каталога Ultra**.
   Дождитесь `pg_is_in_recovery() = false`.
4. Вручную настройте приложения на восстановленную БД, перенесите необходимые
   серверные ключи из отдельной резервной копии. Физическая реплика не копирует
   файлы ключей подписки, SSH, spec и systemd.
5. Подтвердите доступ и подписки тестовым аккаунтом. Прежний primary возвращайте
   только по отдельной процедуре восстановления согласованности; worker не делает
   автоматический rewind или promotion.
