# Happ и домашний прокси

## Старые конфигурации

Обновление ultra не требует перевыпуска основного TCP/REALITY/Vision-профиля:
сохраняются `public_host`, `vless_port`, UUID, REALITY-ключи, SNI и short IDs.
Не меняй эти поля при включении новых listeners. Старые `/client` и основные поля
ответа сохраняются. Новый `entry_id` равен `primary`; ID основных профилей прежние.
Источник: [экспорт и проверки совместимости](../internal/config/profile_integration_test.go).

XHTTP-профиль публикуется только при настроенном listener. При обновлении
XHTTP/REALITY сохраняй порт, путь и REALITY-параметры. Диапазон padding должен
включать стандарт ядра 100–1000 для совместимости существующих клиентов.

## Подписка

Отдельный адрес на стандартном HTTPS-порту: [настройка входа](subscription-ingress.md).

1. Настрой HTTPS бота по [канонической инструкции TLS](../deploy/TLS.md).
2. На тестовом VLESS-пользователе в Mini App нажми «Выдать / заменить подписку».
3. Сохрани показанную ссылку. «Открыть в Happ» открывает HTTPS-страницу ultra
   во внешнем браузере; на ней нажми «Добавить в Happ». Если приложение не открылось,
   скопируй ссылку и добавь подписку в Happ вручную.
4. Обнови подписку: доступны «Автоматически» и по одному профилю на опубликованную страну.

Прямой `happ://` внутри Telegram WebView может не открыться. Используется
[openLink](https://core.telegram.org/bots/webapps#initializing-mini-apps) для своей
HTTPS-страницы с отдельным нажатием на deep link. Токен передаётся во фрагменте URL
и удаляется из истории страницы; сторонние сервисы перенаправления не используются.
Источник: [страница импорта](../internal/bot/embed/miniapp/happ.js).

Публичный endpoint требует TLS. При TLS termination на reverse proxy бот принимает
`X-Forwarded-Proto: https` только от loopback; proxy должен перезаписывать этот заголовок.

Ссылка — секрет. Существующая ссылка восстанавливается через keyring без ротации;
явная замена закрывает прежнюю ссылку. «Отозвать подписку» запрещает обновления, но уже скачанные
конфиги продолжают работать. Для отзыва доступа к VPN отключи пользователя или смени UUID.
Подписка не требует платного provider ID. Автоматический выбор при запуске Happ
не гарантирует переключение уже открытого соединения.

Ответ подписки содержит стандартный `support-url` на существующего Telegram-бота.
Happ показывает его отдельной кнопкой; `/start member` возвращает кнопку личного
кабинета и не обрабатывается как административное приглашение. Username получается
через Telegram `getMe` и атомарно сохраняется вместе с автономным кешем подписок:
после перезапуска или при недоступном Telegram используется последнее подтверждённое
значение. Некорректное или ещё неизвестное имя убирает только кнопку, не саму подписку.
Прямой `profile-web-page-url` не используется: внешняя страница не получает
Telegram initData для авторизации.
Источники: [API](../internal/adminapi/subscriptions.go),
[Happ app management](https://github.com/HappDev/happ_su/blob/main/dev-docs/app-management.md),
[публичный обработчик](../internal/bot/subscriptions.go).

## JSON-подписка с выбором входа

`/sub/<token>` по умолчанию возвращает прежние VLESS URI. Флаг spec
`happ_default_json` (по умолчанию `false`) включает массив полных Xray-конфигураций
для клиента с продуктовым токеном `Happ` в User-Agent; неизвестные клиенты получают URI.
Перед включением нужно проверить фактический User-Agent устройства и переключение
входов на Android через Wi-Fi и мобильную сеть. `?format=happ` и `?format=uri`
явно выбирают представление независимо от флага. `?transport=xhttp-tls` выбирает
прежний URI-вход; сочетание с `format=happ` возвращает 400.
Прокси передаёт User-Agent и только параметры `format`, `transport` и `preview`;
ответы имеют `Cache-Control: no-store` и `Vary: User-Agent`.

Для ограниченной приёмки spec принимает `subscription_preview_bridges` — список
публичных параметров по тому же формату, что `subscription_bridges`. Он используется
только запросом `?format=happ&preview=reserve` владельца административного доступа.
Обычная подписка этот список не публикует. Отказ проверки владельца возвращает
503, отказ в разрешении — 404. Пробная выдача не обслуживается автономным кешем.
Для обоих тестовых входов явно задавай `fingerprint: "firefox"`.
`?format=happ&preview=reserve-test` выдаёт четыре профиля: оба входа,
недоступный основной, недоступный резерв и оба недоступны. Требуются ровно два
preview-дескриптора (TLS и REALITY). Недоступность моделируется адресами в `.invalid`
только в полученном JSON; общие listeners и серверные маршруты не меняются.
Балансировщик и блокирующий fallback сохраняются. Эта проверка подтверждает выбор
при недоступности на старте; внезапный отказ уже работающего пути требует отдельного
контролируемого испытания. Первые восемь разрешённых preview-запросов за жизнь relay
записывают только User-Agent длиной до 256 байт в защищённый серверный журнал,
без URL, токена, IP или идентификатора владельца — для проверки распознавания клиента.

Бот получает флаг и оба представления в одном подтверждённом поколении кеша.
Ключ кеша учитывает эффективный формат и транспорт; User-Agent не смешивает URI и JSON.
При недоступности relay действует последнее подтверждённое поколение до исходного
срока 24 часа, включая его флаг. Откат флага начинает действовать автономно после
успешного обновления кеша; при недоступной БД нельзя подтвердить новый режим.
После отката пользователю достаточно обновить прежнюю подписку: UUID и токен не меняются.
Источник контракта: [общий выбор формата](../internal/config/subscription_format.go).

### Изолированная проверка внезапного отказа

[Временный TCP-forward](../deploy/happ-acceptance-forward.py) предназначен только
для согласованной приёмки. Он перенаправляет два отдельных тестовых TCP-порта
на существующие loopback-входы TLS и REALITY, не принимает ключей или UUID.
Порты нужно заранее проверить на свободу; их открытие и выдача тестового preview
выполняются оператором отдельно. Файл управляющего Unix socket должен находиться
в существующем каталоге `0700`, принадлежащем запускающему UID; socket имеет `0600`.
По умолчанию оба пути закрыты. Внешний bind требует root, срок работы — максимум
час. Завершение или TTL закрывают listeners и тестовые потоки. Общие входы не меняются.
Пример только для локального стенда (порты выбирает оператор):

```sh
python3 deploy/happ-acceptance-forward.py --control /tmp/happ-test-private/control.sock serve --primary-port 25443 --reserve-port 25444 --ttl 900
python3 deploy/happ-acceptance-forward.py --control /tmp/happ-test-private/control.sock up all
python3 deploy/happ-acceptance-forward.py --control /tmp/happ-test-private/control.sock status
python3 deploy/happ-acceptance-forward.py --control /tmp/happ-test-private/control.sock down primary
```

Оператор выдаёт административному владельцу preview с адресами этих aliases,
сохраняя Firefox и остальные параметры входов. TCP-перенаправление сохраняет
half-close; выключение пути завершает только его тестовые соединения. Статус содержит
монотонное время и счётчики соединений без адресов и пользовательских данных.
Регрессии: `python3 scripts/test-happ-acceptance-forward.py`.

На Android сначала подтвердить работу обоих тестовых адресов в Wi-Fi и мобильной
сети: нестандартный порт может блокироваться самой сетью, и такой результат не
доказывает дефект переключения. Затем не переподключать VPN и не менять профиль.
Без дополнительных приложений достаточно браузера с HTTPS-страницей, показывающей
публичный IP: открыть страницу, выполнить пинг Happ и повторить свежие загрузки.
Для однозначного начала оператор включает только основной alias и подтверждает
передачу данных. Затем включает резервный и сразу выключает основной, фиксируя время
команды и время первой успешной свежей загрузки с IP разрешённого exit. Цель — не более
60 секунд. Повторить обратный переход из работающего только резервного пути.
Счётчики активных соединений включают проверки Observatory и сами по себе не доказывают,
какой путь передаёт пользовательские данные. Затем закрыть оба на 120 секунд:
новые загрузки должны перестать работать.
Восстановление aliases должно вернуть новые загрузки за 60 секунд.
Браузерный сценарий проверяет пользовательское поведение TCP, но сам по себе
не подтверждает UDP или отсутствие любого фонового прямого трафика устройства.

Для расширенной проверки необязательно использовать Termux с Python:
[probe](../scripts/happ-acceptance-probe.py) создаёт новые HTTPS-соединения и уникальные
UDP DNS-запросы, печатает только время, успех и IP HTTPS-выхода. HTTPS URL задаётся
оператором и должен возвращать JSON `{"ip":"..."}` либо trace с `ip=...`.
До VPN проверить доступность назначения и запомнить прямой IP устройства. Через VPN
успех допускается только с известными IP exit. При отключении обоих aliases должны
пропасть TCP и UDP-ответы; после возврата — восстановиться за 60 секунд.
Перехват DNS внутри клиента может имитировать UDP-успех, поэтому полноценная приёмка
UDP требует отдельного подтверждения уникальных запросов на выходе тестового пути.
Длительные существующие TCP-сессии могут оборваться: критерий относится к новым
соединениям. Тайминг DNS-пробы и браузера не следует выдавать за пакетный аудит всего
устройства.

Auto и страны используют общий выбор профилей и прежние UUID. Каждый JSON-профиль
содержит все записи `subscription_bridges` из spec, `leastPing` и BurstObservatory
с проверками каждого входа раз в 10 секунд и таймаутом 5 секунд.
`sampling: 1` оценивает последний результат, чтобы старый успех не скрывал отказ.
При отсутствии рабочих входов `fallbackTag` направляет соединение в `blackhole`:
все TCP/UDP-соединения проходят через catch-all правило балансировщика.
Первый outbound также блокирующий. Отдельная проверка пинга JSON в HAPP
не заменяет проверку сайтов через запущенный VPN.
Клиентского прямого выхода нет; `/client` и URI-экспорт сохраняют прежнее поведение.

`subscription_bridges` — отдельный статический список публичных параметров для
проверки клиентской схемы. Он заменяет основной вход в JSON-профилях, если задан;
пустой список использует текущий основной listener. Это не кластерный реестр:
он не устанавливает узлы, не синхронизирует пользователей и не подтверждает применение.
`public_entries` продолжает описывать TCP-перенаправления.

```json
{
  "subscription_bridges": [
    {"id":"region-a", "host":"ingress-a.example.net", "port":443,
     "public_key":"PUBLIC_REALITY_KEY", "server_name":"example.com", "short_id":"0123456789abcdef"},
    {"id":"region-b", "host":"ingress-b.example.net", "port":8443, "transport":"xhttp", "path":"/transport",
     "public_key":"OTHER_PUBLIC_REALITY_KEY", "server_name":"example.com"}
  ]
}
```

Публикуй только заранее настроенные входы с одинаковыми UUID Auto и стран;
Старые записи без `security` означают REALITY. `security: "tls"` требует
`transport: "xhttp"`, `server_name` и `path`, без REALITY-ключа и short ID.
Для одного bridge можно сочетать HTTPS и отдельный REALITY-порт; это резерв транспорта,
а не защита от потери VM или IP. Параметры берутся с соответствующей ноды, приватные
ключи в список не входят. Для приёмки JSON-переключения на Android проверь импорт
и обновление одного URL, Auto и страны, отключение/возврат каждого входа без обновления
подписки. Критерий — восстановление новых соединений до 60 секунд и блокировка
при отказе обоих входов.
Работа Go Xray в транспортном тесте не подтверждает, что HAPP сохраняет JSON при импорте.

TLS-ошибка при правильных параметрах REALITY может означать несовместимость
ClientHello с библиотекой сервера; текущая фиксация совместимости описана
в [разработке](development.md). Успешный тест новым Xray не исключает этот случай.

Если `public_host` задан IP-адресом, публичные TCP/XHTTP-входы bridge исключают
этот IP из подмены назначения по HTTP Host/TLS SNI. Так проверка REALITY,
попавшая в уже работающий VPN, сохраняет адрес bridge вместо перехода на сайт
маскировки. Для доменного `public_host` такое IP-исключение не добавляется.
Источник: [генератор bridge](../internal/config/xray_bridge.go).

Клиентский sniffing — отдельный этап: если повторная проверка REALITY проходит
через локальный вход уже включённого VPN, подмена назначения по SNI может заменить
адрес bridge сайтом маскировки ещё на устройстве. Серверное `ipsExcluded` такую
подмену не исправляет. Для диагностики сравни проверку при выключенном и включённом
VPN, затем повтори её с отключённым «Анализом пакетов / Sniffing» в HAPP.
В самостоятельно управляемом Xray-конфиге `routeOnly: true` сохраняет адрес назначения,
используя найденный домен только для маршрутизации. URI-подписка ultra не управляет
этой настройкой локального входа HAPP; не переключай её на JSON ради диагностики.
Проверяй отдельно обновление прежней подписки через включённый VPN: успешный запрос
к проверочному сайту не подтверждает доступность HTTPS-входа подписки.
Источники: [sniffing Xray](https://xtls.github.io/en/config/inbound.html#sniffingobject),
[управление HAPP](https://github.com/HappDev/happ_su/blob/main/dev-docs/app-management.md).

После аварийной замены единственного bridge на Android обновите **существующую**
подписку в HAPP, затем переподключите VPN. Не нажимайте «Выдать / заменить подписку»:
это ротирует токен. Проверьте сайты сначала через «Автоматически», затем через каждую
опубликованную страну; при временном отказе её exit работает серверный резерв. При смене IP или утрате старого
REALITY-ключа сохранённые до обновления профили не заработают. С одним bridge проверка
переключения между входами невозможна; её проводят после добавления второго.

Источники: [JSON-экспорт](../internal/config/happ.go),
[транспортная проверка](../internal/config/happ_integration_test.go),
[Xray routing](https://xtls.github.io/en/config/routing.html).

## Дополнительные listeners

`anti_censor.public_xhttp_port` включает XHTTP/REALITY. Новый `public_xhttp_tls`
задаётся в spec bridge отдельно; основной порт сохраняется:

```json
{
  "public_xhttp_tls": {
    "port": 8443,
    "server_name": "access.example.net",
    "certificate_file": "/etc/ultra/public/fullchain.pem",
    "key_file": "/etc/ultra/public/key.pem",
    "path": "/connect",
    "mode": "stream-up"
  }
}
```

Это фрагмент spec, не готовая установка. Домен должен указывать на доступный вход,
сертификат — покрывать `server_name`; файл ключа доступен только пользователю relay.
Listener использует H2 и не использует Vision. Выпуск сертификата, firewall и обновление
рабочего spec выполняются отдельным этапом по инструкциям установки.
`mode: packet-up`, `xmux` (поля закреплённого Xray) и `download` с `address`, `port`,
`server_name` — только для отдельных испытаний. Download-адрес должен обслуживать тот же
путь и пользователей, с проверяемым TLS; поле не создаёт удалённый listener автоматически.
Экспорт `extra` сохраняет эти параметры, но их сохранность после импорта в Happ требует проверки.
Наличие `public_xhttp_tls` само по себе не добавляет профиль в подписку. Эксперимент публикуется через отдельный descriptor по серверной роли владельца, см. раздел «Постоянный основной вход и эксперимент».

Для диагностики существующий URL принимает `?format=uri&transport=xhttp-tls`: Auto и страны используют опубликованный основной XHTTP, либо прежний TLS listener, если основной не настроен. Отсутствующий listener возвращает 503. Этот параметр не раскрывает скрытый эксперимент; сочетание с `format=happ` отклоняется.

Источник: [общие настройки клиента/listener](../internal/config/xhttp_tls.go).

Резервный вход добавляется только после проверки уже созданного TCP passthrough:

```json
{"public_entries": [{"id": "backup", "host": "backup.example.com", "tcp_port": 443}]}
```

Опциональные `xhttp_reality_port` и `xhttp_tls_port` публикуют forwarding для соответствующего
listener bridge. Значение `0` исключает профиль. UUID и SNI сохраняются; новый ID имеет
вид `backup/fast_tcp_reality`. См. [границы дополнительных входов](censorship-resistance.md).

## Домашний Linux-сервер

Создай отдельного VLESS-пользователя ultra и сохрани его ответ `/client` в закрытый файл.
`ultra-client` принимает этот JSON, старый ответ с `full_xray_config_base64` либо полный
JSON Xray. Сборка: `make build-client`; для другого хоста используй `GOOS=linux` и его `GOARCH`.

```sh
./ultra-client -config client-export.json -profile fast_tcp_reality
curl --proxy socks5h://127.0.0.1:10808 https://probe.example.net/plain-ip
curl --proxy http://127.0.0.1:10809 https://probe.example.net/plain-ip
```

SOCKS5 и HTTP слушают только loopback. `socks5h` передаёт имя назначения прокси;
SOCKS5 с предварительным локальным DNS может вернуть неправильный адрес до входа в туннель.
Для сервисов используй `ALL_PROXY=socks5h://127.0.0.1:10808` либо
`HTTPS_PROXY=http://127.0.0.1:10809` и `HTTP_PROXY=http://127.0.0.1:10809`.
Поддержка переменных зависит от приложения; `NO_PROXY` создаёт прямые исключения.
Проверяй фактический выход и доступность Gemini, а не только запуск процесса.

Для постоянной работы скопируй бинарник в `/usr/local/bin/ultra-client`, создай системного
пользователя/группу `ultra-client`, каталог `/etc/ultra-client` с правами `0750` и файл
`client.json` с правами `0640`, доступный этой группе. Установи
[unit systemd](../deploy/ultra-client.service), затем выполни `systemctl daemon-reload`
и `systemctl enable --now ultra-client` **на своём домашнем сервере**.
`Restart=on-failure` восстанавливает процесс. Для резерва задай другой `-profile`
через override `ExecStart` и явно перезапусти unit; скачанные конфиги автоматически не обновляются.

`-render output.json` создаёт новый файл `0600` для самостоятельного запуска Xray.
Публичный SOCKS bridge не нужен. Для контейнера удобен host networking на Linux;
доступ из отдельной Docker-сети/LAN требует отдельного gateway/firewall с разрешёнными
клиентами. CLI намеренно отвергает non-loopback bind; не открывай этот no-auth proxy всему LAN.
Источник: [ultra-client](../cmd/ultra-client/main.go).

## Приёмка клиента

Локальные тесты проверяют закреплённый Xray; они не заменяют проверку приложений Happ.
Пока версия не записана после реального испытания, платформа не считается принятой:

| Платформа | Проверенная версия Happ | Импорт / XHTTP extra / обновление / ручной резерв |
| --- | --- | --- |
| Android | не проверена | требуется проверка на устройстве |
| iOS / iPadOS | не проверена | требуется проверка на устройстве |
| macOS | не проверена | требуется проверка в приложении |
| Windows | не проверена | требуется проверка в приложении |
| Linux | не проверена | требуется проверка в приложении |

На каждой платформе проверь DNS и охват приложений в VPN/TUN-режиме. URI не управляет
системной DNS-политикой Happ. Для проксируемых назначений нужен удалённый DNS без системного
fallback; автоматические исключения российских приложений ultra не добавляет.
Для Gemini проверяй вход в аккаунт и отправку запроса: HTTP 200 стартовой страницы недостаточно.
Сравни маршрут и регион аккаунта с [официальными ограничениями Gemini](https://support.google.com/gemini/answer/14579026?hl=en).

## Личный кабинет и локации

Для приглашённых пользователей доступен [личный кабинет](enrollment.md): повторное
копирование возвращает прежнюю подписку. Профиль «Автоматически» выбирает доступный разрешённый exit по приоритету
независимо от прежнего выбора в Mini App. Профиль локации предпочитает её exit, но при отказе или исчерпании квоты
переходит на другой исправный выход с доступной пользовательской квотой и общим бюджетом. Кабинет показывает серверные маршруты, а не выбранный профиль
приложения. Добавленные локации появляются после обновления подписки.

В подписке публикуется один профиль «Автоматически» и один профиль на
опубликованную страну. Страна определяется географическими метаданными exit; узлы без
страны, выключенные и неопубликованные не добавляются. Временный отказ health и
исчерпание квоты не удаляют профиль и не меняют его UUID: маршрут выбирается на bridge,
а при отсутствии разрешённого резерва трафик блокируется. Несколько узлов одной
страны объединяются по приоритету, затем стабильному ID. Технический `/client` сохраняет все
транспорты и прежние UUID: старые скачанные конфиги продолжают работать.
Источники: [отбор подписки](../internal/adminapi/subscription_profiles.go),
[стабильность URI и JSON при смене health](../internal/adminapi/subscription_profiles_test.go).

`Server-Timing: relay` показывает время получения ответа от relay; медленные публичные
ответы (от секунды) записываются как `slow subscription response` без URL и токена.
Этот замер не включает DNS/TLS и передачу между устройством и сервером.

Для упрощённой подписки выбран XHTTP/REALITY, если настроен основной
`anti_censor.public_xhttp_port`. При отсутствии этого listener используется
существующий TCP-профиль; несуществующий XHTTP-порт не публикуется. Выбор транспорта
одинаков для автоматического профиля и стран. Серверный TCP-listener, UUID и старый
`/client` сохраняются. Это выбор продукта, а не доказательство меньшей вероятности
блокировки в конкретной сети: необходимы измерения от клиента. Возможности XHTTP
описаны [разработчиками Xray](https://github.com/XTLS/Xray-core/discussions/4113).

## Таймаут обновления через WARP

Успешное открытие страницы подписки напрямую не проверяет путь через VPN.
Сравнивайте HTTPS-вход через текущий exit и его WARP: SOCKS-отказ WARP может
проявляться в Happ как таймаут. На exit с WARP параметр
`anti_censor.warp_direct_domains` задаёт точные домены, выходящие напрямую с exit.
Для собственного сервиса подписки добавьте только его домен; default TCP-маршрут
остаётся через WARP. Это выход из exit, а не прямой трафик с устройства или bridge.
См. [генератор exit](../internal/config/xray_exit.go).


## Переключение и месячный лимит

Профиль «Автоматически» переключается на исправный резерв на bridge и возвращается
к основному после 60 секунд устойчивого восстановления; обновлять подписку не нужно. Кабинет показывает подтверждённый маршрут и незавершённое
применение отдельно. При переключении старые соединения закрываются; приложение
открывает новые. Это может кратко затронуть другие устройства и пользователей.

На всех выходах Vultr действует один личный потолок: 25% подтверждённого
начисленного пула аккаунта после 20% запаса. Доступный объём также ограничен общим
остатком провайдера; смена региона или пересоздание exit не возвращают квоту.
На статическом exit действует отдельный общий бюджет.
При исчерпании узла Auto выбирает другой исправный выход с доступной квотой;
если допустимого выхода нет, VPN-трафик блокируется. Профиль страны использует
другой выход только при наличии квоты; удалённая локация остаётся заблокированной. Отсутствие обрыва интернета не означает обход квоты.
Расход всех профилей и устройств суммируется, смена UUID не сбрасывает его.

Квота резервируется на диске до передачи данных, общими порциями до 256 КиБ на
владельца и exit. Неиспользованная после аварии часть не возвращается. Измеренная
статистика сохраняется каждые пять секунд и может отличаться от консервативного списания.
Подробности расчёта и требования к данным провайдера — [квоты Vultr](vultr.md).

### Метаданные лимита подписки

URI- и Happ JSON-подписки передают общую пользовательскую квоту управляемых выходов
в единственном стандартном `subscription-userinfo`: `upload=0`, `download` —
учтённый расход владельца, `total` — его личный потолок. Формат Happ предоставляет
одну такую строку потребления; дополнительные информационные блоки не являются
второй независимо измеряемой квотой и требуют provider ID. Выходы с отдельным
бюджетом поэтому показываются в личном кабинете, а не суммируются с общей строкой.
Месячный сброс не является окончанием подписки, поэтому `expire` отсутствует.
При неизвестном лимите или отсутствии подтверждённого измерения числовой заголовок
не выдаётся, сама подписка доступна.

Публичное представление не раскрывает провайдера: профили называются по странам,
а API и кабинет используют `quota_kind=shared|separate|direct` и подписи
«Общая квота», «Отдельная квота», «Напрямую». Внутренние provider scope и названия
сохраняются в учёте и административных экранах. `announce` перечисляет страны общей
и отдельной квоты, а `X-Ultra-Quota-Scope` использует нейтральное значение `shared`.
`announce` содержит UTF-8 текст в формате `base64:…`; состояние, период, время
измерения и сброса доступны в `X-Ultra-Quota-State`, `X-Ultra-Quota-Period`,
`X-Ultra-Quota-Observed-At` и `X-Ultra-Quota-Resets-At`.

Автономный кеш сохраняет последние подтверждённые значения до истечения своих
24 часов, добавляет `X-Ultra-Quota-Freshness: stale`, время подтверждения
`X-Ultra-Cache-Confirmed-At` и предупреждение в `announce`. Он не обновляет
расход, лимит или период при переходе месяца. Для текущего остатка требуется
успешное обновление из управляющего API.
Источники: [метаданные](../internal/adminapi/subscription_quota.go),
[кеш бота](../internal/bot/subscription_cache.go).

## Постоянный основной вход и эксперимент

### Проверка соединения в HAPP

Тип проверки задаётся в приложении отдельно от VLESS-профиля. Для проверки доступности
входа можно выбрать **TCP** вместо **Via Proxy GET**: TCP измеряет установление
соединения с bridge без TLS и запроса к тестовому сайту. Это не проверка авторизации,
выбранного exit или передачи данных через VPN; после неё отдельно проверяй сайты
и новые медиа. Сам VPN при смене типа проверки остаётся зашифрованным.

При разборе сбоев выключи «Пинг при запуске» в настройках подписок и сравни работу
одного профиля до и после одной проверки. Via Proxy проверяет более длинный путь;
сбой после неё сам по себе не доказывает сетевую блокировку. ICMP в HAPP требует
временного отключения туннеля. Принудительный `ping-type` через подписку требует
Provider ID; ultra его не задаёт, пользователь выбирает тип в HAPP.
Источники: [виды проверок HAPP](https://www.happ.su/main/ru/faq/ping),
[управление параметрами приложения](https://www.happ.su/main/dev-docs/app-management).

### Входы и публикация

Параметр `fingerprint` в XHTTP/TLS endpoint задаёт клиентский TLS-отпечаток для URI, JSON и отдельного download-соединения. Допустимы `chrome` и `firefox`; отсутствие поля сохраняет `chrome`. Основной вход и эксперимент задают его независимо. Отпечаток не меняет серверный TLS listener, UUID или токен. Ручная правка профиля в HAPP может быть заменена при обновлении подписки, поэтому проверенное значение закрепляется в конфигурации публикации.

`primary_xhttp` задаёт публичные `host`, `port`, `server_name`, `path`, `mode`, `xmux` и отдельный loopback `backend_port`. TLS завершается в Nginx; backend не содержит сертификатов. `published: false` подготавливает listener без переключения обычной подписки. При публикации Auto и страны используют этот вход, сохраняя токены и UUID. `/client` и явный JSON используют тот же основной транспорт. `legacy_public_enabled: false` отключает публичные REALITY-входы; без этого параметра прежние установки совместимы.

`experimental_profile_file` — атомарно опубликованный JSON с `host`, `endpoint` (публичные параметры XHTTP/TLS) и loopback `status_port`. Закрытые файлы сертификатов в descriptor запрещены. Подписка перечитывает descriptor без reload основного relay. Профиль «Эксперимент · XHTTP TLS» добавляется только если связанный Telegram-аккаунт владельца подписки является администратором. Ошибка определения роли скрывает эксперимент; параметры URL и заголовки роли не задают. Это ограничение видимости: уже сохранённый профиль работает, пока его UUID разрешён.

При снятии отдельного эксперимента сначала удаляют descriptor через реестр владения
и подтверждают успешное обновление кеша подписок; затем останавливают его службу
и удаляют принадлежащие ей файлы. Основной `gateway_vless_port`, Nginx и общий
сертификат не удаляют: ими могут пользоваться другие входы. Перед очисткой
проверяют обязательные пути резервного копирования. Отсутствующий descriptor
скрывает эксперимент без перезапуска relay; ссылку `experimental_profile_file`
убирают из исходного spec при следующем обновлении конфигурации.

Отдельный процесс `ultra-relay -transport-spec PATH` принимает транспорт и передаёт VLESS-поток с PROXY protocol в `gateway_vless_port` основного relay, доступный только на loopback. Он не подключается к БД и не измеряет пользовательский трафик повторно. Ошибка или перезапуск эксперимента не перезапускает основной процесс. Основной relay остаётся общей зависимостью. UDP/XUDP проходит внутри авторизованного VLESS; отдельный публичный UDP listener не требуется.

В административной диагностике `public_ingresses` показывает готовность основного и экспериментального входов отдельно. Это серверная проверка TLS/backend, не подтверждение доступа из сети телефона. Android — обязательная клиентская приёмка; совместимость остальных HAPP-платформ ожидается, но не объявляется проверенной без испытания.

Установка, сертификаты и откат описаны в [постоянном входе](xhttp-ingress.md), долгосрочная граница — в [ADR 0017](adr/0017-xhttp-ingress.md).

## Подготовка резервного REALITY-входа

Для внезапного отказа только тестового пути бот поддерживает
`format=happ&preview=reserve-live`. По умолчанию режим недоступен. Переменная
`ULTRA_HAPP_ACCEPTANCE_FILE` указывает приватный обычный JSON-файл без symlink
с SHA-256 токена (`token_digest`), `issued_at`, `expires_at` и отдельными
`primary_port` / `reserve_port`. Срок не больше часа, права файла — `0600`.
Бот сначала получает административный `reserve` preview у relay, затем заменяет
только порты. Авторизацию владельца, UUID, адреса, TLS и обычные подписки он не
меняет. Другая подписка, истёкший файл или ошибка управляющего API закрывают
режим; автономный кеш для него не используется. Обе ветки обязательны, прямой
`freedom` запрещён. Listener тестовых aliases должен иметь собственный TTL.
Источник: [ограниченная выдача](../internal/bot/happ_acceptance.go),
[регрессии](../internal/bot/happ_acceptance_test.go).

`deploy/prepare-reality-reserve.py` готовит новый приватный spec, не меняет сервисы
и firewall. Нужен действующий опубликованный HTTPS-вход и сохранённые REALITY-ключи.
По умолчанию используется отдельный порт 24443; основные HTTPS-параметры сохраняются,
прежний дополнительный XHTTP/REALITY listener не включается. Обязательный
`--check-binary` проверяет кандидата соответствующим новым relay. До активации
отдельно проверь, что порт свободен на рабочем узле; статическая проверка spec
не обнаруживает listeners других процессов.

Параметр `--publish` требует `--android-accepted`: подтверждение передачи данных
и переключения на Android через Wi-Fi и мобильную сеть. До этого список
`subscription_bridges` не добавляется и основная подписка продолжает выдавать HTTPS.
Смешанный профиль выбирается явным `format=happ`; URI и токен не ротируются.
Локальная [транспортная проверка](../internal/config/happ_integration_test.go) включает
XHTTP/TLS и REALITY, но не заменяет устройство пользователя.
Источник: [подготовка](../deploy/prepare-reality-reserve.py).
