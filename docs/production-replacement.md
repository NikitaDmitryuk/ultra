# Замена production без восстановления старой выкладки

## Политика

При установке новой версии состояние прежней non-DB инфраструктуры считается
одноразовым. Незавершённая выкладка не возобновляется и не откатывается: старые
bridge/exit узлы, deployment-журнал, admission markers, worker jobs и временные
артефакты можно удалить и поднять non-DB парк заново. Допустим полный простой и
потеря состояния этих узлов.

Единственное сохраняемое состояние — PostgreSQL primary и его данные. Операция
замены не должна переустанавливать, сбрасывать, импортировать дамп поверх или
менять endpoint primary. Перед удалением non-DB узлов создаётся свежая
зашифрованная копия БД; проверяются её аутентификация, полный custom-format архив
и восстановление в изолированную тестовую БД. До и после замены сравниваются
идентичность primary и версии схемы. Для кандидата без требуемых миграций схема
должна остаться неизменной.

Кандидат фиксируется immutable manifest-ом и committed SHA. Новый парк ставится
заново с сохранёнными DB endpoint и прикладными данными; секреты и ключи,
необходимые для связи с primary, восстанавливаются из canonical operator inputs.
SSH host keys нового парка проверяются по доверенному источнику. Это единственная
сохраняемая проверка идентичности узлов; прежние deploy receipts и host-bound
recovery proofs не переносятся.

## Граница обещаний

Для старой выкладки не поддерживаются resume, rollback, reconciliation,
supersession и восстановление старых non-DB runtime. Журнал старой выкладки не
является основанием продолжать или блокировать новую полную замену. Его можно
удалить вместе с остальными старыми deployment-артефактами после остановки или
удаления прежнего non-DB парка.

Удаление только локального `operation.json` не останавливает удалённые jobs.
Полная замена обязана удалить прежние non-DB узлы или их runtime до запуска
нового controller, чтобы прежние исполнители не продолжали работу с primary.
Обычная очистка или новый запуск `make deploy` поверх старого runtime не считается
полной заменой.

После замены подтверждаются неизменность primary/schema, успешный `doctor`,
готовность сервиса, соединение настоящего VPN-клиента и открытие сайта через VPN.
Резервная копия остаётся средством возврата данных при фактической потере БД;
здоровую primary поверх неё не перезаписывают.

## Текущее состояние реализации

Обычный `make deploy` остаётся upgrade-путём и при dispatched операции может вернуть
`manual_supervised_operation_conflict`. Для полной замены реализован отдельный
`make replace-production`: он требует свежую зашифрованную копию с проверенным
изолированным restore, receipt, закреплённые commit/manifest, новый state directory
и явное подтверждение `replace-non-db-preserve-postgresql`. Для dispatched журнала
также требуется исходный config, связанный с его SHA-256. Команда сначала выполняет
read-only проверки и fencing/quiescence старых non-DB исполнителей, затем очищает
только non-DB runtime/state и ставит новый парк, сохраняя PostgreSQL primary.
Инвентаризация включает обязательный список известных Ultra-служб и найденные
systemd units; `list-unit-files` с кодом 1 считается пустым совпадением только
при пустых stdout и stderr, остальные ошибки systemd останавливают замену.
Contained bootstrap-controller получает фиксированное per-user пространство
execution admission и при запуске в уже разрешённой systemd unit, и при создании
отдельной transient unit.

Если проверка обнаруживает неизвестный SSH helper/session или активную DB client
transaction, команда останавливается до удаления. Primary identity/schema
считывается до fencing; после этого fencing затрагивает только non-DB targets,
а перед очисткой отдельный primary census проверяет SSH sessions и активные DB
transactions без ещё одного непосредственно предшествующего SSH probe к primary.
Это сохраняет DB gate и не классифицирует хвост собственного probe как посторонний
операторский сеанс. Retained-primary recovery-команды и
`rebuild-non-db preflight` для этого пути не используются.

Краткоживущий root `sshd-session` в `ssh.service` повторно проверяется полным
census каждые 250 мс, не дольше 15 с по общему monotonic deadline. Replacement
продолжится только после успешной полной проверки и исчезновения всех процессов
исходной session; PID churn не продлевает deadline, а сохраняющиеся процессы,
новые блокеры и ошибки census останавливают cleanup.
