# HTTPS-вход подписок

Отдельный вход передаёт зашифрованный HTTPS боту на bridge. Он обслуживает Mini App,
`/happ` и `/sub/…`, не переносит БД, сертификаты или секреты на exit. Решение —
[ADR 0012](adr/0012-permanent-subscription-ingress.md).

## Постоянный вход через SSH

Для Амстердама используется существующий nginx. В локальном `install.config`
задать `BOT_INGRESS_MODE=ssh`, `BOT_INGRESS_IP`, `BOT_DOMAIN` и после DNS-перехода
`BOT_PUBLIC_URL=https://DOMAIN`. Используются `SSH_USER` и `IDENTITY` локального
установщика. Запуск: `bash scripts/setup-subscription-ingress.sh`.

Предпосылки: nginx с модулем stream и включением `/etc/nginx/stream.d/*.conf`
в секции stream основного конфига, свободный 443 и доступные 80/443/8444 в firewall.
SSH-режим не меняет firewall и не включает выключенный firewall автоматически.
Он не обращается к Vultr и не снимает защиту старого ingress. Отсутствующие
предпосылки исправляются до запуска; nginx/Vultr не подменяются незаметно.

[Скрипт nginx](../deploy/setup-subscription-ingress-ssh.py) управляет только
`stream.d/bot-proxy.conf` и `conf.d/acme-proxy.conf`. Принимаются прежние известные
конфигурации ultra либо файлы с сохранённым управляющим хешем; чужие файлы и
символические ссылки отклоняются. Ошибка проверки или reload восстанавливает
старые файлы и проверяет восстановление nginx. Повтор без изменений не делает reload.
HTTP access log отключён: путь подписки содержит секрет. TLS завершается на bridge.

Перед удалением сменного узла: подготовить новый вход, проверить сертификат и
старую подписку, заменить A-запись, выдержать прежний TTL и проверить обычный DNS
и фактическое подключение. Затем остановить прежний HTTPS-прокси и повторить
проверки. Только после успеха удалить старое значение
`ULTRA_SUBSCRIPTION_INGRESS_INSTANCE_ID` из конфигурации relay, применить её
контролируемым перезапуском и проверить снятие защиты через API/UI. Сохранить
конфигурацию старого прокси для отката DNS; UUID и токены не менять.

## Альтернативный управляемый вход Vultr

`BOT_INGRESS_MODE=vultr` — прежний режим и значение по умолчанию для совместимости.

На выбранном существующем узле установить HAProxy. В
[шаблоне](../deploy/subscription-ingress.cfg) заменить `BRIDGE_IP` на IPv4 bridge,
проверить `haproxy -c -f …`, сохранить предыдущую конфигурацию и подключить шаблон.
Предварительно проверить, что порты 80, 443 и 8444 свободны. Открыть в firewall
узла и провайдера только эти дополнительные TCP-порты IPv4; AAAA не публиковать
без отдельной проверки IPv6. TLS завершается на bridge: HAProxy не хранит ключи.

443 и прежний 8444 передаются на bridge:8444. На 80 разрешены только запросы
`/.well-known/acme-challenge/`: они передаются на bridge:80 для существующего
certbot standalone. Остальные HTTP-пути получают отказ. Не включать HTTP access
logs или захват URL: путь подписки содержит секрет. HAProxy пишет события
доступности backend, не содержимое запросов; статистику соединений проверять
локально через systemd/ss. TCP health-check не заменяет проверку TLS и HTTP.

У бота `-public-url https://DOMAIN` или `ULTRA_BOT_PUBLIC_URL=https://DOMAIN`
задаёт публичный HTTPS origin независимо от `-port`. Допустим только origin без
учётных данных, пути, query и fragment. Флаг имеет приоритет над окружением;
пустое значение сохраняет прежнее построение URL из domain/port. Это меняет
выдаваемые ссылки, но не UUID, токены и listener.

## Проверка и переключение

До изменения DNS проверить с `curl --resolve DOMAIN:443:INGRESS_IP` страницу
`/happ`, Mini App, JS и подписку тестового пользователя. Повторить для 8444 и
через внешний VPN; для SOCKS с `--resolve` использовать `socks5://`, чтобы
проверить заданный адрес, а не старую DNS-запись через `socks5h://`.
Секретный путь передавать только внутри защищённого проверяющего процесса,
не показывать body подписки или URL в выводе.

Если проверки проходят, изменить A-запись на ingress IP. Прежний bridge:8444
оставить работающим. После обновления DNS проверить обычное разрешение с разных
резолверов, импорт/обновление старой ссылки и сертификат. Только затем включить
публичный origin без порта, но только после истечения прежнего TTL с момента
смены A-записи. Успех нескольких публичных резолверов не исключает старый кеш
у клиента: bridge:443 обслуживает REALITY и выдаёт сертификат другого имени.
До истечения TTL сохранять ссылки с 8444: этот порт работает на обоих IP.
При таком сбое вернуть прежний публичный URL и заново открыть Mini App,
поскольку кабинет кеширует полученную ссылку в памяти страницы.
Проверить `certbot renew --dry-run` на bridge и
наличие [deploy-hook перезапуска бота](../deploy/renew-ultra-bot.sh): файловый TLS загружается при старте процесса.
Не заменять рабочий сертификат результатом staging-проверки.

## Эксплуатация и откат

Оба узла обязательны для доступа к подпискам. Это не отказоустойчивая копия бота.
Перед удалением или заменой exit, используемого как ingress, перенести вход и DNS;
автоматизация Vultr сама такой перенос не выполняет. Минимальное изменение DNS
TTL не отменяет уже закешированный старый TTL.

Для отката вернуть прежнюю A-запись и убрать override публичного URL. Сохранять
вход 8444 на обоих адресах до истечения DNS-кешей. При отказе нового IP через
проверяемый VPN не переключать DNS: отдельно исследовать доступность домена и
рассматривать новый собственный домен без автоматической покупки.

## Воспроизводимая установка и защита

В локальном `install.config` задаются `BOT_INGRESS_IP`, `BOT_PUBLIC_URL` и
`BOT_INGRESS_INSTANCE_ID` (ID VPS, не ID операции). Файл не коммитится.
В режиме `vultr` команда `bash scripts/setup-subscription-ingress.sh` запускается с локального компьютера,
подключается к bridge и использует его существующий ключ автоматизации для exit.
Ключи остаются на bridge; скрипт находит только VPS сохранённой операции Ultra.
При пустом ID разрешается однозначное совпадение управляемого VPS по ingress IP.

Сначала развернуть relay с поддержкой защиты. Скрипт устанавливает HAProxy,
добавляет отсутствующие firewall-правила и deploy-hook, сохраняет предыдущую
конфигурацию. Чужую или вручную изменённую конфигурацию HAProxy не перезаписывает.
Он не меняет DNS и публичный URL. После первого создания защитного drop-in
`relay_restart_required=True` требует контролируемого перезапуска relay; повторный
запуск не перезапускает рабочее ядро. До подтверждения защиты через API новый вход
не публиковать. Повторная настройка другого защищённого VPS требует явного переноса.

`ULTRA_SUBSCRIPTION_INGRESS_INSTANCE_ID` в конфигурации relay запрещает удаление,
замену и продолжение разрушительных этапов worker для обслуживающего подписки VPS.
API возвращает `409 ingress_in_use`; карточка содержит `serves_subscription_ingress`.
Отключение только VPN-выхода не удаляет HTTPS-вход. Это защита внутри Ultra;
ручное удаление через кабинет провайдера ею не перехватывается.

`make verify-miniapp` использует системный resolver для реального публичного
TLS-соединения, проверяет фактический IP и HTTP 200. Backend проверяется отдельно
с корректным SNI. Ошибка публичного пути не скрывается успехом backend.
Установщик сохраняет публичный URL на сервере, если локальный override не задан.

Для ограниченного наблюдения после выпуска есть [read-only сборщик](../deploy/observe-release.py):
он запускается на bridge с `--hours 24 --public-url https://DOMAIN:8444 --output PATH`.
Результат содержит только счётчики, состояние проверки и время завершения. Он не
пишет токены, профили, тела ответов или исходные сообщения журналов и не меняет
маршруты. Это серверное наблюдение; оно не заменяет приёмку Happ и пользовательской сети.
