# Перенос bridge на другой сервер

Процедура переносит bridge между двумя Linux-хостами через SSH. Exit-ноды не
переустанавливаются. Скрипт не обращается к Yandex Cloud API: публичный IP, DNS и
security groups переключает владелец облака в явно обозначенной точке.

Переносятся конфигурация и ключи REALITY, PostgreSQL, пользователи, exit-ноды,
подписки, состояние бота и автоматизации, установленные бинарники и нужные
сертификаты. PostgreSQL переносится логическим dump/restore. Каталог данных
PostgreSQL и весь `/etc/letsencrypt` не копируются.

## Ограничения

- Источник и цель должны быть Debian или Ubuntu на Linux/amd64.
- PostgreSQL primary должен находиться на bridge. Поддерживается URI
  `postgres://` или `postgresql://` с loopback-host и стандартным портом 5432;
  libpq DSN и нестандартные порты отвергаются до остановки source.
  Если bot переопределяет `ULTRA_DB_DSN`, он должен указывать на ту же БД;
  перенос отдельной базы бота этим сценарием не поддерживается.
- Основная версия PostgreSQL на цели должна совпадать с источником. Если нужных
  пакетов нет, подготовьте репозиторий пакетов до окна; скрипт не обновляет major.
- Цель — выделенная VM без чужих установок Ultra, прикладных БД PostgreSQL
  и сертификатов для других доменов.
  Поддерживается Certbot standalone/HTTP-01; нестандартные plugins/hooks требуют
  отдельной подготовки и блокируют автоматический перенос.
  `stage` проверяет renewal-конфигурацию без обращения к ACME; Certbot на цели
  должен быть не старее источника. Настоящий renewal dry-run выполняйте отдельно
  после согласования сетевого доступа и окна, он не входит в локальные тесты.
- Оператор должен иметь `root` или passwordless `sudo` по SSH на обоих хостах.
- SSH-адреса обоих хостов должны оставаться доступными после переключения
  сервисного IP. При переносе единственного публичного IP используйте внутренние
  адреса через bastion/VPN либо стабильные aliases из `~/.ssh/config`.
- SSH host keys должны быть заранее проверены по доверенному каналу и записаны в
  указанный `known_hosts`. Скрипт использует `StrictHostKeyChecking=yes`.
- В окне переноса нельзя менять пользователей, маршруты и облачные операции.
- Старую VM нельзя удалять до завершения периода наблюдения.
- Фазы выполняет один оператор последовательно, без параллельных запусков.

Логический restore создаёт другой PostgreSQL-кластер: прежние физические реплики
на exit не могут автоматически продолжить его WAL. Их данные и службы скрипт
не трогает. На новом bridge сохраняются ключи и конфигурация, но репликационные
и Vultr provisioning-воркеры остаются отключёнными через последний
`EnvironmentFile` в `zzzz-bridge-migration.conf`. Не удаляйте этот drop-in до
отдельной процедуры пересоздания реплик и проверки pending cloud operations.
Старые записи `streaming` в БД не доказывают актуальность резервных копий.

Обычный `make install` не заменяет эту процедуру. `REUSE_BRIDGE_SPEC` читает
состояние с целевого bridge, но не переносит PostgreSQL и серверные файлы с
другого хоста.

## Что запросить у владельца новой VM

- SSH-адрес, имя пользователя с passwordless `sudo` или `root`, временный
  публичный IP и fingerprint host key.
- Cloud, folder и VM ID, зону доступности, новый статический IP и подтверждение
  правил security group.
- Ресурсы не меньше отчёта `preflight`, особенно свободный диск.
- Возможность синхронно переключить сеть и при необходимости вернуть её назад.
- При переносе IP между облаками: согласие владельца, квоту целевого облака и
  номер встречного обращения в поддержку.

Владельцу передаются только публичный SSH-ключ, исходящий CIDR оператора,
требования к VM/портам из `preflight`, зона, окно работ и данные заявки на перенос
IP. Приватные SSH-ключи, `install.config`, `.env`, Telegram/Vultr tokens, DB DSN и
содержимое `/etc/ultra-relay` владельцу не передаются.

Это ограничение обмена доступами, а не изоляция от владельца: имея root или
контроль VM, он сможет прочитать перенесённые ключи, токены и БД. Новый сервер
должен находиться в доверенном контуре; SSH и права `0600` не скрывают секреты от root.

## Публичный IP в Yandex Cloud

Перед **остановкой** VM для снимка диска или переустановки ОС проверьте, что её
публичный адрес статический. Остановка освобождает динамический IP; последующий
запуск не сохраняет прежний адрес. Закрепление адреса выполняется до остановки,
а не только перед отвязкой (см. [правила динамических адресов](https://yandex.cloud/ru/docs/vpc/operations/set-dynamic-ip)).

Внутри одного облака статический адрес можно переместить в каталог новой VM и
перепривязать при совпадении зоны доступности. Между разными облаками Yandex Cloud
требует два согласованных обращения в поддержку — от облака-источника и
облака-приёмника. До переноса адрес делают статическим и отвязывают, а в целевом
облаке проверяют квоту.

Если перенос заранее не подтверждён, используйте новый статический IP. До окна
добавьте его в provider firewall и UFW каждой exit-ноды для SSH, репликации и
tunnel-порта. Старый адрес удаляйте только после приёмки. При смене
`spec.public_host` обновите существующую подписку в Happ: её URL, токен и UUID
сохраняются. Отдельно импортированные профили без подписки нужно переимпортировать.

Официальные инструкции:

- [перенос IP между облаками](https://yandex.cloud/ru/docs/troubleshooting/vpc/how-to/move-external-ip-between-cloud);
- [перепривязка IP между VM](https://yandex.cloud/ru/docs/compute/operations/vm-control/vm-transferring-public-ip).

## Доступ после смены IP

Проверьте каталог и зону **самой VM**, а не только defaults `yc`: адреса и квоты
относятся к выбранному cloud/folder. Нормальный экран загрузки с приглашением
login не объясняет отказ SSH; до переустановки проверьте сеть и журналы через
доверенный консольный доступ. Новый SSH host key сверяйте по этому каналу,
не отключая `StrictHostKeyChecking`.

У Vultr две независимые границы доступа: firewall сервера пропускает SSH и
туннель, а allowlist API-ключа разрешает исходящий IP bridge для автоматизации.
Добавьте новый `/32` в обе; сохранённое правило firewall не доказывает доступ API.
HTTP 401 может означать запрет IP, поэтому сначала проверьте API ACL и безопасно
прочитайте причину отказа, не выводя ключ и не заменяя его без необходимости.

`ULTRA_VULTR_BRIDGE_IP` может быть задан в systemd drop-in, а не в основном
`EnvironmentFile`. Сверяйте эффективную настройку и все подключённые файлы,
не выводя секретное окружение. После изменения нужны `daemon-reload` и перезапуск
relay с [проверкой готовности до запуска бота](development.md).
Источники: [настройки cloud worker](../cmd/ultra-relay/cloud.go) и
[миграционный helper](../scripts/bridge-migration-state.py).

Если подписка и Mini App обслуживаются отдельным HTTPS ingress, смена
`spec.public_host` не переключает его backend. Обновите upstream на ingress,
сохраните прежние домен, порт и ключи подписки и проверьте публичный TLS/HTTPS.
Правила провайдера и статус создания VPS принимайте только после фактической
передачи HTTPS через опубликованный клиентский профиль.

## Восстановление ОС из остановленного диска

Это отдельная аварийная процедура, не режим `migrate-bridge.sh`. До остановки
зарезервируйте публичный IP, сохраните исходный диск и полный снимок; учитывайте
`auto_delete` boot-диска перед удалением VM. Исходную VM не запускайте одновременно
с восстановленным bridge. Снимок и диск оставьте до приёмки и периода наблюдения.

Физическое восстановление PostgreSQL допустимо из **полностью остановленного**
кластера с совместимой основной версией, сохранёнными control/WAL/slots,
конфигурацией, владельцами и внешними tablespaces, если они есть. Не копируйте
работающий PG-каталог. В отличие от логического restore, сохранённая физическая
идентичность позволяет прежним репликам продолжить WAL; подтвердите это текущими
`pg_stat_replication` и `pg_stat_wal_receiver`, а не старой записью `streaming` в БД.
При несовместимости используйте логический перенос с пересозданием реплик.

Восстановите units/drop-in, ключи автоматизации и доверенные exit host keys внутри
сервера. Проверьте владельцев файлов и loopback-only `listen_addresses` PostgreSQL:
SSH-репликация не требует публичного 5432. После диагностики верните исходные
настройки временного консольного доступа. Обычный установщик не восстанавливает
эти данные и не заменяет аварийную процедуру.

После внезапного отказа bridge старый SSH reverse-forward может продолжить слушать
`15432` на exit и мешать новому подключению. Проверьте listener и соединения:

```bash
ss -lntp 'sport = :15432'
ss -ntp 'sport = :22'
```

Перед закрытием сессии сопоставьте PID и исходящий IP с **прежним остановленным**
bridge. Завершайте только эту сессию, а не все `sshd`; затем дождитесь нового
соединения и живого WAL receiver в состоянии `streaming`. Источник:
[SSH-репликация](../internal/install/remote.go).

## Подготовка

На машине оператора нужен репозиторий Ultra, `ssh`, проверенный `known_hosts` и
локальный Xray для финального client smoke-test. Пример общих аргументов:

```bash
MIGRATE=(
  scripts/migrate-bridge.sh
  --source-host old-bridge-admin --source-user root --source-identity ~/.ssh/old
  --target-host new-bridge-admin --target-user deploy --target-identity ~/.ssh/new
  --known-hosts ~/.ssh/known_hosts
)
```

Скрипт не читает локальные `.env` и `install.config`. Приватные данные идут
напрямую `source SSH → target SSH`, не сохраняются в рабочем каталоге и не
выводятся в журнал.

### 1. Preflight

```bash
"${MIGRATE[@]}" preflight
```

Команда только читает состояние. Она проверяет ОС, архитектуру, CPU/RAM, место,
локальность БД, loopback Admin API и измеряет размер и длительность сжатого
`pg_dump`. Если цель уже содержит чужую установку Ultra, проверка завершается
ошибкой. Повторный запуск для уже подготовленной тем же источником цели допустим.

Место проверяется по файловым системам каталогов назначения, временного архива
и backup, а не только `/`. В объём входят внешние ключи, geo-assets и явно
настроенные каталоги состояния. Окно 5–15 минут — предварительная оценка:
`stage` дополнительно измеряет реальный dump/restore; учтите финальный перенос
файлов, контроль содержимого БД и сетевое переключение.

Отчёт перечисляет ingress-порты для владельца. Обычно это:

- `22/tcp` только с CIDR оператора;
- публичный VLESS-порт, обычно `443/tcp`;
- опциональный public XHTTP-порт;
- bot HTTPS-порт и `80/tcp` для ACME HTTP-01;
- `10810-10899/tcp`, только если используются публичные per-user SOCKS.

PostgreSQL наружу не открывают. Исходящий доступ нужен к exit-нодам, Telegram,
DoH/HTTPS и репозиториям пакетов.

### 2. Stage без простоя

```bash
"${MIGRATE[@]}" stage
```

`stage` устанавливает системные зависимости на цели, сохраняет прежнее целевое
состояние в `/var/backups/ultra-bridge-migration`, потоково переносит файлы и
восстанавливает предварительный dump. Архив и его manifest временно хранятся
только на целевом сервере в закрытом каталоге; после импорта архив удаляется.
Переносятся units/drop-in, используемые `EnvironmentFile`, `ULTRA_*_KEY_FILE`,
`ULTRA_*_STATE_DIR`, geoip/geosite и ACME-account активного bot-домена.
После распаковки проверяются хеши файлов и цели символических ссылок.
Затем relay кратко запускается во временном systemd-unit с исходными настройками,
включая capabilities для порта 443, но без Vultr API и replication worker.
Проверяются spec, БД и первичная
загрузка Xray; после проверки relay останавливается. Bot не запускается, поэтому
конфликта Telegram long polling нет.

Повторный `stage` идемпотентен для той же пары серверов и создаёт новый backup
перед перезаписью. Он запрещён после начала cutover. При изменении файлов
работающего source во время копирования возможен отказ проверки хешей — повторите
`stage`; финальная согласованная копия выполняется только в `freeze`.
Маркер проверяет machine ID обоих серверов. Старый маркер без привязки пары
не принимается автоматически; не удаляйте его вслепую для обхода защиты.
Если source сам находится в состоянии незавершённой миграции с pause-drop-in,
сначала завершите его предыдущую процедуру; новый перенос блокируется.

### 3. Freeze в окне работ

```bash
"${MIGRATE[@]}" freeze --confirm FREEZE
```

Сначала сохраняется исходное состояние автозапуска и активности служб, затем
отключается их автозапуск и останавливаются bot и relay на старом bridge.
Certbot timer/service также приостанавливаются, чтобы deploy-hook не запустил
старый bot; при rollback восстанавливаются их прежние состояния.
После подтверждения остановки повторно копируются **файлы и конфигурация**, затем
выполняется финальный dump/restore. До запуска проверяются файловые хеши и
контрольная сумма содержимого public-таблиц БД (включая UUID, exit и bot-состояние).
При ошибке скрипт восстанавливает исходные службы source только после
подтверждённой остановки target. Если остановку target подтвердить нельзя,
автоматический запуск source запрещён — требуется ручное разбирательство.
При успехе оба bridge остаются выключенными, а скрипт сообщает о
готовности к сетевому переключению.

### 4. Действие владельца облака

Владелец переносит и привязывает старый IP либо подтверждает маршрутизацию нового
IP/DNS на target. Скрипт не может выполнить этот шаг и не принимает cloud token.

При смене IP перед активацией должны быть одновременно разрешены старый и новый
адреса на exit-нодах. Для установки с Vultr automation передайте отдельно:

```bash
--new-public-host NEW_PUBLIC_IP --new-bridge-ip NEW_PUBLIC_IP
```

Если клиентский `public_host` — DNS, `--new-public-host` можно не задавать, но
`--new-bridge-ip` всё равно нужен для firewall/provisioning при смене исходящего IP.

### 5. Activate

С сохранённым IP:

```bash
"${MIGRATE[@]}" activate \
  --target-public-ip TARGET_BACKEND_IP \
  --verify-ip-url https://YOUR_PROBE/plain-ip --expected-exit-ip EXPECTED_EXIT_IP \
  --network-ready --confirm ACTIVATE
```

С новым IP:

```bash
"${MIGRATE[@]}" activate \
  --new-public-host NEW_PUBLIC_IP --new-bridge-ip NEW_PUBLIC_IP \
  --target-public-ip TARGET_BACKEND_IP \
  --verify-ip-url https://YOUR_PROBE/plain-ip --expected-exit-ip EXPECTED_EXIT_IP \
  --network-ready --confirm ACTIVATE
```

Скрипт атомарно меняет только host-dependent значения, добавляет вычисленные
порты в активный UFW, запускает relay и ждёт успешного initial reload и active
exit. Bot запускается только после этой проверки. При ошибке target-сервисы
останавливаются, source автоматически не запускается: к этому моменту сеть уже
могла быть переключена владельцем.

### 6. Verify

```bash
"${MIGRATE[@]}" verify \
  --target-public-ip TARGET_BACKEND_IP \
  --verify-ip-url https://YOUR_PROBE/plain-ip --expected-exit-ip EXPECTED_EXIT_IP
```

Проверяются systemd, loopback Admin API, reload, active exit, пользователи,
контрольные суммы бинарников, публичный Mini App с валидным TLS и существующий
end-to-end сценарий `client → bridge → exit → internet`. Для отдельного ingress
используется сохранённый `ULTRA_BOT_PUBLIC_URL`. `--skip-client-test` разрешён
только как явное временное исключение и не является полной приёмкой.

`activate` сначала проверяет relay и клиентский маршрут, затем запускает bot,
проверяет Mini App и включает Certbot timer. Без успешного клиентского probe
активация не завершается; `--skip-client-test` допускается только в `verify`.
При отказе любой проверки target останавливается и отключается его автозапуск;
source автоматически не запускается после сетевого переключения.

Probe должен возвращать **обычный текстовый IP** с успешным HTTP-кодом и иметь
домен, направляемый текущими правилами через выбранный exit. Непустой ответ или
HTTP-ошибка не считаются успехом. При необходимости выберите существующего
активного VLESS-пользователя через `--verify-user-uuid`; новых пользователей
скрипт не создаёт. На машине оператора нужен совместимый Xray.

`--target-public-ip` — адрес HTTPS-backend бота, не SSH-alias. При отдельном ingress
добавьте `--miniapp-ingress-ip INGRESS_IP`: проверка отдельно сверяет публичный
TLS/DNS peer и прямое соединение к target с правильным SNI.

Отдельно проверьте Mini App/TLS и реальное клиентское устройство. При новом IP
убедитесь, что подписка экспортирует новый адрес, и попросите пользователей
обновить **прежнюю подписку**, не создавая новый токен. Проверьте Auto и каждую
разрешённую фиксированную страну передачей HTTPS, а не только статусом в кабинете:
серверная проверка exit не проверяет публичный вход и клиентское устройство.

## Rollback

Во время приёмки запрещены административные изменения. Relay может успеть записать
только статистику трафика; она не синхронизируется обратно автоматически.

Сначала остановите target:

```bash
"${MIGRATE[@]}" rollback --confirm ROLLBACK
```

Владелец возвращает IP/DNS на source. После подтверждения:

```bash
"${MIGRATE[@]}" rollback --network-restored --confirm ROLLBACK
```

Если target уже был активирован, требуется дополнительное осознанное подтверждение:

```bash
--allow-post-activate-data-loss
```

Оно допустимо только при отсутствии изменений пользователей, маршрутов и облачных
операций. Для отката после штатной эксплуатации нужна отдельная обратная миграция
БД, а не этот аварийный путь.

То же подтверждение требуется после неудачной активации: relay мог уже записать
статистику. После `stage`, до `freeze`, rollback только останавливает target —
source ещё не менялся. После ошибки `freeze` выполните новый успешный `stage`
перед повторным cutover. После ошибки активации используйте rollback; не
перезаписывайте живой узел повторным `stage`.

## Завершение

После периода наблюдения удалите старый bridge IP из firewall exit-нод и выключите
старую VM. Удалять VM, диск и освобождать IP следует отдельным действием после
проверки клиента, Mini App, TLS и логов. Возобновление резервных PostgreSQL-копий —
отдельная задача с явным разрешением изменений на exit.
