# Перенос bridge на другой сервер

`ultra-install bridge-migrate` переносит существующую установку через фиксированные
Ansible-операции. Конфигурация читается из `install.config`, секреты — из `.env`.
Второй inventory вручную не создаётся. SSH host keys обоих стабильных операторских
адресов должны быть заранее подтверждены; SSH aliases/config и неизвестные pins
не используются. Один bridge остаётся единственным primary.

## Что переносится

Финальное зашифрованное поколение создаётся после остановки relay и бота: оно
содержит закрытый локальный журнал учёта, согласованный логический dump PostgreSQL,
ключи, UUID, токены подписок, сертификаты, настройки, точные артефакты и состояние
автоматизации. Формат и проверка поколений общие с [восстановлением](../deploy/recovery/RESTORE.md).
Ключ age используется только на машине оператора; на исходный и новый сервер его
не копируют. Частная расшифрованная staging-копия остаётся у оператора до окончания
проверки и должна быть удалена после сохранения проверенного зашифрованного поколения.

## Требования

- Источник — Debian/Ubuntu Linux/amd64, цель — Ubuntu 24.04 Linux/amd64; единственный локальный
  PostgreSQL 16 primary на 5432. На цели Python 3.12 и достаточно ресурсов.
- Цель выделена для переноса: чужие прикладные БД, установки и сертификаты
  отвергаются до остановки источника. SSH root или passwordless sudo доступны
  на обоих стабильных адресах, независимо от публичного IP сервиса.
- На операторской машине имеется проверенный Ansible-комплект, age и приватная
  офлайн-копия age-ключа. `--job-dir` находится в приватном каталоге и сохраняется
  между фазами. Его родитель владеет общей блокировкой операций.
- Сервисный IPv4 можно заменить или сохранить при переносе адреса. Для одинаковых
  адресов обязательна типизированная идентичность двух разных машин: machine-id,
  разные закреплённые SSH endpoints и свежая проверка остановленного прежнего PG.
  Совпавший IP сам по себе не является доказательством изоляции.
- Поддерживаются управляемые прямые DNS-входы и существующий принадлежащий ultra
  forwarding-вход. Чужую конфигурацию Nginx операция не перезаписывает.
- Во время окна нельзя параллельно менять топологию. Постоянный исполнитель
  резервирует lifecycle и дожидается текущих прикладных операций до фиксации данных.

## Фазы

Общие аргументы передаются каждой фазе. Все SSH-файлы и age identity — абсолютные
пути; примеры ниже являются placeholders:

```bash
ultra-install bridge-migrate preflight \
  --config /private/install.config --job-dir /private/migration/job \
  --source-host 192.0.2.10 --target-host 192.0.2.20 \
  --source-identity /private/source-key --target-identity /private/target-key \
  --known-hosts /private/known_hosts
```

1. `preflight` проверяет ОС, machine-id, ресурсы, PostgreSQL, выбранные TLS/Certbot
   webroot-настройки, чужое состояние цели и текущий публичный вход. Вывод безопасен;
   подробные доказательства сохраняются приватно, а не печатаются в терминал.
2. `stage` устанавливает зависимости и пользователей только на цели. Источник
   продолжает работать. Рабочую БД и открытый журнал на этом шаге не копируют.
   Повтор до cutover допустим; после заморозки данных повторная stage запрещена.
3. `freeze --confirm FREEZE --age-identity /private/offline-age-key`
   прекращает новые управляющие операции, останавливает писателей, создаёт финальное
   зашифрованное поколение и persistently маскирует источник вместе с действительным
   PostgreSQL cluster unit. На цель восстанавливаются проверенные данные и БД;
   приложение остаётся остановленным. Нужны `--new-bridge-ip`,
   `--new-bridge-provider` и при смене имени `--new-public-host`.
   Если фаза падает до cutover, источник возобновляется только после подтверждения,
   что целевой PG не принимает записи. Неоднозначный ответ оставляет источник
   изолированным и операцию неуспешной.
4. Оператор переключает сеть и подтверждает её готовность.
   `activate --confirm ACTIVATE --network-ready --verify-ip-url https://example.net/ip
   --expected-exit-ip 198.51.100.30` пересоздаёт физические реплики, запускает relay,
   проверяет реальную передачу данных через **новый** bridge и только затем бот.
   Проверочный клиент закрепляет адрес цели, сохраняет SNI/ключи и исключает прямой
   выход и прежний bridge. Неуспешная проверка останавливает цель; старый primary
   автоматически не включается после cutover.
5. Тот же сценарий проверяет прямой DNS либо owned forwarding-вход, публичный
   HTTPS, затем включает автоматизацию. Блокировка записи освобождается до пассивного
   ожидания свежей независимой копии и актуальных реплик, чтобы фоновые проверки
   могли завершиться. Успех записывается только после этих доказательств.
6. `verify` повторяет фактический туннель и готовность копий/реплик. Нужны те же
   `--verify-ip-url` и `--expected-exit-ip`. Установочные операции повторно не выполняются.

Каждая фаза повторно проверяет обе закреплённые машины и закрытый PG источника.
Журнал задания связывает endpoints, пару машин и поколение: возобновление не
подменяет их новым сервером или другой копией. После успешно выполненного rollback
для нового переноса нужен новый приватный job-каталог и новая пустая цель.

## Откат

`rollback --confirm ROLLBACK` сначала подтверждает остановку приложения и PG цели.
Без `--network-restored` источник остаётся выключенным: нужно вернуть публичную
сеть на старый адрес и повторить фазу. При подтверждённой сети возвращаются прежние
сохранённые systemd definitions и исходные активные службы, включая автоматизацию.
После начала активации нужен явный `--allow-post-activate-data-loss`: новые записи
на цели не переносятся обратно. Квоты, расход и БД нельзя безопасно «откатить»
заменой только бинарника или повторной первоначальной установкой.

Исходную VM, проверенные зашифрованные поколения и совместимый аварийный комплект
сохраняйте до окончания наблюдения. После смены публичного адреса достаточно обновить
существующую подписку; токены и UUID не ротируются. Отдельно импортированные профили
без подписки обновляются отдельно.

## Восстановление ОС из остановленного диска

Это отдельная аварийная процедура, не режим `ultra-install bridge-migrate`. До остановки
зарезервируйте публичный IP, сохраните исходный диск и полный снимок; учитывайте
`auto_delete` boot-диска перед удалением VM. Исходную VM не запускайте одновременно
с восстановленным bridge. Снимок и диск оставьте до приёмки и периода наблюдения.

Старый диск или клон снимка может иметь те же UUID файловой системы и PARTUUID,
что и новый загрузочный диск. При `root=UUID=...` гостевая ОС способна загрузиться
с вторичного диска, даже если облако назначило загрузочным другой. Сверьте `blkid`
для обоих дисков, `root=` в `/proc/cmdline` и `findmnt -n -o SOURCE /`.
После копирования отсоедините восстановительный диск перед перезагрузкой,
сохранив сам диск и снимок. Не меняйте UUID смонтированной корневой файловой системы.
После загрузки повторно подтвердите источник `/` и PG-каталога.

Физическое восстановление PostgreSQL допустимо из **полностью остановленного**
кластера с совместимой основной версией, сохранёнными control/WAL/slots,
конфигурацией, владельцами и внешними tablespaces, если они есть. Не копируйте
работающий PG-каталог. В отличие от логического restore, сохранённая физическая
идентичность позволяет прежним репликам продолжить WAL; подтвердите это текущими
`pg_stat_replication` и `pg_stat_wal_receiver`, а не старой записью `streaming` в БД.
При несовместимости используйте логический перенос с пересозданием реплик.

Восстановите units/drop-in, ключи автоматизации и доверенные exit host keys внутри
сервера. Проверьте владельцев файлов и loopback-only `listen_addresses` PostgreSQL:
SSH-репликация не требует публичного 5432. После диагностики верните исходные
настройки временного консольного доступа. Обычный установщик не восстанавливает
эти данные и не заменяет аварийную процедуру.

После внезапного отказа bridge старый SSH reverse-forward может продолжить слушать
`15432` на exit и мешать новому подключению. Проверьте listener и соединения:

```bash
ss -lntp 'sport = :15432'
ss -ntp 'sport = :22'
```

Перед закрытием сессии сопоставьте PID и исходящий IP с **прежним остановленным**
bridge. Завершайте только эту сессию, а не все `sshd`; затем дождитесь нового
соединения и живого WAL receiver в состоянии `streaming`. Источник:
[SSH-репликация](../deploy/ansible/roles/replica/tasks/main.yml).
