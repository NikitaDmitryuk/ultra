# Vultr: границы интеграции exit-нод

Управление доступно администратору в «Сервис → Серверы»: предложение цены,
создание, наблюдение, повтор этапа, замена региона и удаление. Операции выполняет
worker bridge с состоянием в PostgreSQL. Установка готовой машины с локального
компьютера сохраняется: [README](../README.md). Каталог и цену нужно проверять
перед каждой покупкой; наличие API-ключа не подтверждает готовность оплаты.

Подтверждение создания держит отдельную короткую блокировку только на время
проверки списка Vultr и записи брони. Долгие этапы worker используют независимую
блокировку; ключ короткой блокировки не совпадает с блокировками маршрутов,
пользователей и учёта трафика. Поэтому изменение локации не должно останавливать
подтверждение другого сервера; сохранённые операции продолжают учитывать занятые слоты.

Лимит считает каждую уникальную физическую VPS, включая машины с одинаковой меткой
операции. Бронь добавляет слот только когда ей ещё не соответствует одна машина;
несколько одинаковых меток не уменьшают фактический размер парка.

После отключения маршрута обычное удаление сохраняет резерв адреса до tombstone:
повторное включение, изменение узла и создание alias на том же хосте запрещены.
Перед каждым разрушительным этапом worker повторяет проверки идентичности и
защищённых хостов, общие с retirement. Старые фазы `delete`/`cleanup` продолжают
читаться. Отмена подготовки с созданным firewall завершается только после его
очистки; при отказе можно повторить этот этап без покупки VPS.

Пятиминутный срок предложения ограничивает подтверждение администратором.
Подтверждённая бронь переживает ожидание worker и долгую подготовку; перед покупкой
worker повторно сверяет цену и наличие плана до и после подготовки. Изменённая цена
или отсутствие мощности останавливают покупку и требуют нового предложения.
Это относится и к созданию exit, и к замене региона. Источник:
[цепочка покупки](../internal/cloud/service.go),
[регрессии очереди и подготовки](../internal/cloud/offer_lifetime_test.go).

## API, необходимый ultra

Базовый URL: `https://api.vultr.com/v2`. Авторизация: `Authorization: Bearer …`.
JSON-запросы используют `Content-Type: application/json`. Списки имеют cursor pagination:
нужно читать все страницы, а не считать первую полным каталогом.

| Метод и путь | Назначение |
| --- | --- |
| `GET /regions` | ID региона, город и код страны для интерфейса ultra |
| `GET /plans?type=vc2` | Ресурсы, базовая цена, региональные цены и перечень локаций |
| `GET /regions/{region}/availability?type=vc2` | Текущее наличие выбранного плана |
| `GET /os` | Выбор актуального Linux x64 образа |
| `GET/POST /ssh-keys` | Найти или зарегистрировать публичный SSH-ключ |
| `POST /firewalls`, `POST /firewalls/{id}/rules` | Создать firewall и разрешения |
| `POST /instances` | Создать VPS и получить `instance.id` |
| `GET /instances/{id}`, `GET /instances` | Наблюдать состояние и получать полный список существующих VPS аккаунта |
| `GET /account/bandwidth` | Уже начисленные credits и общий исходящий расход аккаунта (`gb_out`) за месяц |
| `GET /instances/{id}/bandwidth` | Входящие и исходящие байты по датам |
| `DELETE /instances/{id}` | Удалить VPS; выключение не прекращает оплату |

Источники: [API](https://www.vultr.com/api/), официальный Go SDK:
[instances](https://github.com/vultr/govultr/blob/master/instance.go),
[regions](https://github.com/vultr/govultr/blob/master/region.go),
[plans](https://github.com/vultr/govultr/blob/master/plan.go),
[OS](https://github.com/vultr/govultr/blob/master/os.go),
[SSH](https://github.com/vultr/govultr/blob/master/ssh_key.go),
[firewall groups](https://github.com/vultr/govultr/blob/master/firewall_group.go),
[firewall rules](https://github.com/vultr/govultr/blob/master/firewall_rule.go).

## Существенные особенности контракта

- Для обычного `POST /instances` массив ключей называется **`sshkey_id`**.
  Поле `ssh_key_ids` из Terraform или instance templates нельзя механически копировать.
  Остальные нужные поля: `region`, `plan`, `os_id`, `label`, `tags`, `hostname`,
  `firewall_group_id`, `disable_public_ipv4`, `backups`, `ddos_protection`.
  Источник: `InstanceCreateReq` в SDK instances выше.
- В публичном ответе `/plans` есть `hourly_cost` и `location_cost`: региональная цена
  может отличаться от `monthly_cost`. В просмотренной модели `govultr.Plan` этих полей
  нет — перед выбором SDK проверить закрепляемую версию; для расчёта цены нужна полная
  модель ответа. Источники: [публичный каталог](https://api.vultr.com/v2/plans?type=vc2)
  и SDK plans выше. Наличие региона в плане не гарантирует свободной мощности.
- API возвращает `status`, `power_status`, `server_status`, `main_ip`.
  Это состояние VM, а не проверка ultra. После выделения IP нужны готовность SSH,
  завершение bootstrap, запуск relay и передача через полный туннель.
- `user_data` передаётся в base64 и доступен через API чтения user-data.
  Base64 не защищает секреты: токен Vultr, ключ bridge и секреты управления не должны
  попадать в cloud-init. Источник: [cloud-init](https://docs.vultr.com/how-to-deploy-a-vultr-server-with-cloudinit-userdata).
- Ответ Instance может содержать `default_password` и ссылку `kvm`; полный ответ
  нельзя писать в логи. Источник: модель Instance в SDK.
- API требует включённого доступа, действующего ключа и подходящих правил
  `Access Control List` организации. Для работы без привязки к IP bridge в
  кабинете Vultr включают `Enable Any IPv4 Access` и `Enable Any IPv6 Access`.
  Тогда смена адреса bridge не требует обновления API allowlist; ограничение
  по IP больше не защищает от использования украденного ключа. Это настройка
  API организации, она не открывает SSH или туннель на exit.
  При ограничении API по IP разрешайте адрес исполнителя облачных запросов, который
  может отличаться от IP bridge. См. [API access](https://docs.vultr.com/support/platform/users/how-can-i-manage-api-access-for-users).
- При превышении 30 запросов/с с одного IP возможен `429`; чтения повторять с backoff.
  SDK по умолчанию использует retryablehttp и лимит трёх повторов. Для создания платного
  VPS автоматические повторы нужно контролировать отдельно: после timeout результат
  может быть неизвестен. Подтверждения idempotency key в изученных источниках нет.
  Метка операции помогает найти ресурс, но не обеспечивает уникальность сама по себе.
  См. [лимиты](https://docs.vultr.com/support/platform/api/what-rate-limits-apply-to-the-vultr-api)
  и [клиент SDK](https://github.com/vultr/govultr/blob/master/govultr.go).

## Установка управляемого exit

Worker создаёт узел выключенным через репозиторий и передаёт его управляемому
Ansible `ConfigureExit` с контекстом, таймаутами и файлами отдельной операции.
Локация публикуется после проверки туннеля. Полная установка bridge и статических
exit выполняется через канонический `make deploy` и bootstrap-подкоманды.

[`POST /v1/exits`](../internal/adminapi/exits.go) регистрирует метаданные узла;
необязательный `enabled` по умолчанию сохраняет включённое состояние.
Ответ содержит параметры туннеля, но не запускает установку на сервере.

Смена региона означает новый VPS и новый адрес; snapshot необязателен, если exit
воспроизводимо устанавливается заново. Оплата пересечения VPS и оставшихся ресурсов
продолжается; месячная квота трафика не выдаётся заново при каждом создании.
См. [перенос](https://docs.vultr.com/support/products/compute/how-do-i-migrate-my-vultr-compute-instance-to-another-datacenter-region),
[биллинг](https://docs.vultr.com/support/platform/billing/how-am-i-billed-for-my-servers),
[квоты](https://docs.vultr.com/support/platform/billing/how-are-bandwidth-caps-calculated).

## Настройка исполнителя

На bridge задайте `ULTRA_VULTR_KEY_FILE` (отдельный файл, не весь локальный `.env`),
`ULTRA_VULTR_SSH_KEY_FILE` и `ULTRA_VULTR_BRIDGE_IP`. У исполнителя должны быть права
на каталог `ULTRA_VULTR_STATE_DIR` (по умолчанию `/var/lib/ultra-relay/vultr`).
При `make deploy` controller и cloud lifecycle drop-in устанавливаются отдельно
от recovery automation. API-ключ передаётся из локального канонического secrets
input; если новый ключ не задан, уже установленный на bridge ключ сохраняется.
На чистом bridge без ключа Vultr create/configure операции работать не смогут.
Файл API-ключа должен принадлежать пользователю relay unit (в штатной установке
`ultra-relay`) и иметь права `600`: файл `root:root` с такими правами сервис
прочитать не сможет, даже если root успешно проверил API тем же ключом.
Сервису также нужны приватный SSH-файл и соответствующий `<файл>.pub`:
подготовка VPS читает публичную часть для регистрации ключа в Vultr. Проверяйте
чтение обоих файлов от пользователя unit; публичный файл `0600 root:root`
блокирует подготовку даже при работающей репликации. Для файла, принадлежащего
root, допустимы `0640 root:ultra-relay`. При восстановлении сохраните пару и
права доступа; приватный ключ не ротируется ради исправления прав публичного.
Источник: [подготовка исполнителя](../internal/cloudinstall/provisioner.go).
Существующий публичный SSH-ключ переиспользуется по криптографическому содержимому:
изменение комментария хоста не создаёт новую регистрацию в Vultr. Невалидные строки
передаются на проверку провайдеру без преобразования. Источник:
[переиспользование ключа](../internal/cloud/vultr.go),
[регрессии](../internal/cloud/vultr_test.go).
При ограничении API по IP разрешите исходящий адрес bridge в Vultr; с `Any IPv4`
и `Any IPv6` эта настройка при смене bridge не нужна. Единый API-ключ используется
для VPS, развёртывания, firewall, SSH-ключей и управления DNS-записями используемой
зоны; доступ к оплате и пользователям не требуется.
Также настройте [копии PostgreSQL](replication.md).

Операция закрепляет копию текущего бинарника bridge; поддерживается Linux amd64.
На exit передаётся минимальный spec туннеля, а не spec bridge. API-ключ Vultr
и ключ подписок не передаются. Firewall разрешает TCP SSH и туннель только с bridge.
Если образ VPS уже включает UFW, установщик отдельно разрешает TCP-порт туннеля
только с `ULTRA_VULTR_BRIDGE_IP`; правила Vultr не заменяют гостевой firewall.
Неактивный UFW установщик не включает. При `verify` с недоступным TCP проверяйте
оба уровня firewall и listener до изменения транспортных настроек.

Облачный IP exit использует собственный самоподписанный сертификат и SHA-256 pin,
даже если основной статический exit bridge использует ACME. При построении каждого
outbound валидный pin IP-адреса выбирает проверку этого сертификата; общая ACME-политика
не отменяет pin. Статический доменный exit сохраняет проверку CA и SNI.
Внутренний TLS-туннель автоматически опускает SNI для IP-адреса exit с валидным
SHA-256 pin. Имя из mimic-пресета не участвует
в проверке такого сертификата, но способно вызвать зависание TLS на сетевом пути
при исправном TCP-пинге. Пустой serverName заставляет официальный Xray использовать
IP назначения, который не отправляется в SNI. Проверка pin остаётся обязательной.
Решение принимается отдельно для каждого exit; доменные и ACME-туннели сохраняют SNI.
`splithttp_tls.sni_mode: send` явно возвращает передачу имени, `auto` — значение
по умолчанию; `omit` и прежнее `omit_sni: true` требуют безопасной конфигурации
для всех exit. Клиентские REALITY и XHTTP/TLS-профили не меняются.
Источник: [генератор туннелей и проверка](../internal/config/tunnel_sni_test.go).

Переустановка bridge и изменение параметров уже созданных Vultr exit выполняются
через транзакционное обновление локального установщика. Worker не переустанавливает
готовые VPS при каждом запуске. Обновление замораживает SSH inventory и topology,
проверяет прежние UUID и сертификаты на узлах, затем применяет настройки с сохранением
идентичности и возможностью rollback. При основном ACME-туннеле разрешён один
статический main и дополнительные managed IP exit с подтверждёнными pins; только
main участвует в ACME checkpoint. Неизвестный узел, отсутствующий pin или несовпадение
сертификата блокируют обновление. Изменение tunnel port по-прежнему требует отдельного
DB checkpoint и не разрешается этой поддержкой смешанного TLS.
Источник: [проверка узла](../cmd/ultra-install/runtime_host.go).

Для неопубликованного VPS с ошибкой на этапе `verify` доступна отдельная команда
«Переустановить на этом VPS». Она возвращает ту же операцию на этап установки с
новым номером попытки, не создавая покупку. Перед записью установщик требует
выключенный exit с тем же operation/node ID, IP экземпляра, прежний SSH host key
и точное совпадение сертификата с pin в БД; после записи pin должен сохраниться.
Каждая новая попытка фиксирует текущий бинарник relay, сформированный spec,
адрес bridge, SSH identity и pinned `known_hosts` в отдельном snapshot; retry и
перезапуск используют именно его. Firewall Vultr сверяется по этому же адресу
bridge до SSH-подключения. Следующая попытка получает новые входы только после
явного retry и подтверждённого завершения предыдущего задания.
Это позволяет исправить старый cloud spec, ошибочно наследовавший ACME от bridge.
Публикация снова требует полной проверки туннеля. Готовые и статические узлы этим
действием не изменяются; для них сохраняется транзакционное обновление выше.

Переустановка требует исключительного владения всем IP: другая запись exit с тем же
IP, даже выключенная или на другом порту, либо другая операция с тем же instance ID
блокирует её. Проверка операции, узла и aliases атомарно сохраняет резерв IP в БД
до SSH preflight. После preflight отдельный CAS привязывает к нему ID неизменяемого
задания перед отправкой worker; он не может восстановить уже снятый резерв.
Создание, обновление, активация и удаление exit проверяют этот резерв;
изменения других IP продолжают работать. Потеря соединения, таймаут и перезапуск
relay не снимают резерв: worker способен продолжать работу без клиента.
После привязки задания резерв снимается только по конечной квитанции worker
(`succeeded` или `failed`). До неё удаление VPS отклоняется, а повтор возобновляет
то же задание и номер попытки. Сбой до привязки задания тоже сохраняет номер попытки;
удаление может снять этот ещё не отправленный резерв через CAS, после которого
поздний submit прежнего исполнителя будет отклонён.
Отсутствующая или недоступная квитанция не подтверждает остановку: резерв сохраняется.
Если неизменяемые входы уже изменились, повтор отклоняется до их согласования;
удалять резерв вручную без подтверждения остановки worker нельзя.
Для операции от старой версии без snapshot установщик сначала проверяет квитанцию:
terminal `succeeded`/`failed` позволяет снять резерв, но не считается успехом новой
установки; затем нужен явный retry с новым номером попытки. При running или
неподтверждённой квитанции резерв остаётся.
Источники: [резерв и блокировки](../internal/db/repo_reinstall_guard.go),
[квитанция worker](../internal/deployansible/service.go).


Предложение действует пять минут и подтверждается конкретным администратором.
Допускается максимум пять занятых слотов и базовая региональная цена до $5/месяц.
Неисправный, создаваемый и удаляемый VPS продолжает занимать слот. При таймауте
POST worker сверяет метку сохранённой операции; покупку автоматически не повторяет.
Неоднозначность требует проверки администратора в панели провайдера.

Новый exit сначала выключен, затем проходит проверку полных тел через туннель,
применение ядром и публикацию профилей. Замена использует свободный слот; старый
VPS удаляется после применения нового. Ошибка удаления видна как незавершённая
операция — остановка VPS не прекращает оплату.

Повтор подтверждения возвращает ту же бронь, включая конкурентные запросы на
последний свободный слот. Повтор удаления сохраняет достигнутый этап
`unpublish` → `delete` → `cleanup`: после ошибки очистки он продолжает очистку,
а завершённая запись `deleted` остаётся завершённой. Поэтому повторный запрос из
Mini App не запускает заново снятие маршрута и не возвращает удалённую VPS в список
занятых слотов. Источники: [worker и действия](../internal/cloud/service.go),
[регрессии повторных запросов](../internal/cloud/action_replay_test.go).

Auto выбирает исправный разрешённый выход по приоритету и не зависит от сохранённого
предпочтения аккаунта. UUID страны предпочитает её exit: при отказе или исчерпании
квоты используется другой исправный выход с пользовательской квотой и общим бюджетом.
При отсутствии разрешённых выходов трафик блокируется; удалённая локация не
превращается в другой действующий доступ. Возврат требует 60 секунд устойчивой исправности.
UUID локации сохраняется при замене VPS в регионе. Обновление подписки не создаёт
профили и не вызывает reload. Старые UUID и ссылки сохраняются.

Источники: [операции](../internal/cloud/service.go), [установщик worker](../internal/cloudinstall/provisioner.go),
[выбор маршрута](../internal/auth/exit_selection.go), [профили](happ.md).

## Журнал и ошибки покупки

Карточка операции содержит понятную причину сбоя и журнал последних 100 событий:
этап, начало/результат, время, длительность и HTTP-код Vultr. Эти события сохраняются
в БД и дублируются в journald с `operation_id`; повторные одинаковые ожидания
неизвестной покупки не засоряют журнал. По ID можно сопоставить Mini App и серверные логи.

Ответы провайдера классифицируются по ограниченному набору признаков. Например,
явное сообщение `insufficient funds` даёт «Недостаточно средств». Один HTTP 403
не считается доказательством нехватки денег или блокировки IP. Неизвестный текст
Vultr не передаётся пользователю и не сохраняется в логах: показываются безопасный
код категории и этап. Секретные поля ответа, пароли VM и ссылки консоли отбрасываются.
[Классификация и тесты](../internal/cloud/errors_test.go),
[журнал](../internal/cloud/events.go).

Отказ `401 Unauthorized IP` означает запрет исходящего адреса worker, а не обязательно
неверный ключ. Публичный каталог и предложение цены могут работать при этом отказе:
авторизованный `GET /instances` проверяется при подтверждении. Ошибки до создания
операции записываются в journald как `cloud request failed` с этапом, кодом и
длительностью; raw-ответ провайдера не сохраняется.
Источник: [облачный API](../internal/adminapi/cloud.go).

Ожидание занятого или недоступного контроллера происходит до этапов отдельных
операций. Worker пишет `cloud worker step failed` с безопасным `code` при смене
причины и `cloud worker recovered` после восстановления; одинаковая ошибка каждые
пять секунд не дублируется. Источник: [worker](../internal/cloud/worker.go).

## Бюджеты выходов

Учёт полезных байтов ведётся по фактическому outbound и суммируется на неизменяемого
владельца для всех UUID и устройств. Период — календарный месяц UTC. На всех выходах
Vultr действует один личный потолок: 25% подтверждённого начисленного пула после
20% запаса, с округлением вниз. Ёмкость берётся из суммы
`instance_bandwidth_credits`, `free_bandwidth_credits` и
`purchased_bandwidth_credits` в `current_month_to_date` ответа
`GET /account/bandwidth`. Vultr начисляет квоту экземпляров почасово; полный
месячный тариф, количество текущих VPS и `current_month_projected` не подтверждают
уже доступный объём. Из начисленного пула один раз вычитается `gb_out` того же
периода, общий для аккаунта и локаций. Создание, остановка и удаление серверов не
сбрасывают уже начисленный или израсходованный трафик текущего месяца. Общий остаток
не распределяется между exit. Отсутствующее, отрицательное или переполняющее
значение любого компонента отклоняет наблюдение вместо выдачи нового бюджета.
При переводе API GB в байты сохраняется десятичный множитель 10⁹; Mini App
показывает байты в двоичных ГиБ/ТиБ, поэтому число на экране может отличаться от GB API.
Источники: [почасовое начисление](https://docs.vultr.com/support/platform/billing/how-are-bandwidth-caps-calculated),
[поля API](https://github.com/vultr/govultr/blob/master/account.go).

Расчётное значение передаётся как `monthly_bytes` и в кабинете администратора
показывается справочно для каждого Vultr-узла. Оно не является тарифом отдельного
узла и не означает, что весь пул доступен одному пользователю. Пользовательский
предел равен 25% безопасной ёмкости после 20% запаса; его остаток дополнительно
ограничен расходом владельца и подтверждённым остатком общего пула. Источник:
[расчёт пула](../internal/cloud/bandwidth.go),
[персональный предел](../internal/db/repo_pool.go), [экран кабинета](../internal/bot/embed/miniapp/cabinet.js).

Принадлежность исторических exit к пулу сохраняется после удаления. Пересоздание,
смена региона и ротация UUID не возвращают расход. Поздние пакеты удалённого
пользователя оплачивают общий пул без восстановления доступа. Перед активацией
неопределённые исторические маршруты требуют установления источника; их расход
не исключается из расчёта автоматически. Биллинг провайдера учитывает исходящий
трафик, тогда как локальный полезный трафик и оплаченные резервы консервативны.

Общее наблюдение содержит локальную отметку перед запросом: последующие списания
уменьшают безопасный остаток. Ошибка API или данные старше 15 минут включают
аварийный режим до 5 ГБ на подтверждённый exit, дополнительно ограниченный общим
и личным остатками, максимум на 24 часа. Перезапуск, смена месяца и новый exit без
подтверждения не создают запас. Источники: [пул](../internal/db/repo_pool.go),
[worker](../cmd/ultra-relay/quota.go), [решение](adr/0019-provider-pool-quotas.md).

Расчёт квот выполняется каждые 30 секунд, запросы провайдера — каждые пять минут.
Успешное применение подтверждает именно прочитанный снимок расчёта; конкурентное
изменение не получает чужое подтверждение. После перезапуска требуется новое
применение. Локальные квоты сохраняются до передачи байтов; неиспользованный хвост
резерва после аварии списывается консервативно. Измеренная статистика и квотное
списание различаются; отличие локальных payload-байтов от биллинга провайдера
сохраняет необходимость запаса.

Общий срок цикла — 90 секунд; отдельный API-запрос ограничен 20 секундами и имеет
ограниченные повторные попытки. Этот срок не заменяет порог
устаревания данных в 15 минут. Предупреждение worker содержит фиксированный этап,
код и доступный HTTP-статус; ответы аккаунта в журнал не попадают.
Запросы расхода и остатка используют общий ограниченный повтор GET при временных
отказах; успешный повтор обязан вернуть свежие данные. Исчерпание повторов
сохраняет ошибку наблюдения; расход ограничивается аварийным резервом либо блокируется
при его отсутствии или исчерпании.

Для самостоятельно установленного основного выхода оператор задаёт запись
`exit_traffic_budgets` с `source='manual'`, месячным бюджетом в байтах и
`is_fallback=true`. Одновременно возможен один основной резерв. Новые Vultr-записи
создаются установщиком автоматически до публикации. UUID fallback — ID узла,
не пользовательский UUID. До изменения сделайте резервную копию БД; неверный
бюджет может исключить основной маршрут. Равные доли пользователей не назначаются.

История, лимиты и использование показаны в личном кабинете и карточке пользователя.
Статус копии PostgreSQL не является состоянием VPN-туннеля: в разделе «Сервис»
они показаны раздельно. Отсутствие данных о диске не отображается как 0 ГБ.

Ошибки подготовительных API-запросов сохраняют фиксированный подэтап (например,
регистрация SSH-ключа или добавление правила firewall) в коде ошибки и сообщении
операции. HTTP-код хранится отдельно; сырой ответ и ID ресурса в код не включаются.
Это позволяет отличить сбой подготовки от отказа покупки. Источник:
[классификация ошибок](../internal/cloud/errors.go).

Удаление имеет две отдельные границы отказа. Синхронная проверка готовности
контроллера может вернуть `lifecycle_busy` или `controller_unavailable` до изменения
операции. Позже, при снятии маршрута, БД запрещает отключить последний включённый
exit; операция завершается с `route_removal_failed`, а запрос удаления VPS к Vultr
не выполняется. После сохранения этапа `retire_unpublish` ID и адрес exit остаются
зарезервированы для retirement, включая ошибки удаления VPS и terminal tombstone
`deleted`: обычные изменения и повторное включение этого узла отклоняются, а retry
продолжает сохранённый этап. IPv4 провайдера сохраняется в операции до снятия
маршрута, в том числе для оплаченного VPS без установленного exit. Все строки `exit_nodes` на этом IP,
кроме собственного сохранённого exit, запрещают explicit retirement независимо от порта
и enabled. Завершённое обычное удаление (`deleted` на этапе `delete`/`cleanup`) освобождает
адрес для нового узла, но сохраняет запрет изменений и повторного создания старого ID.
При обычном удалении нового VPS допускается только disabled историческая строка,
точно связанная с таким завершённым удалением другой operation и другого provider instance;
сохранённый адрес истории, если есть, должен совпадать. Незавершённые удаления,
неизвестные aliases и explicit retirement сохраняют строгие ограничения. Повторные этапы и ответ provider 404 заново проверяют сохранённый адрес,
алиасы, bridge, основной exit и физический DB primary. Старый retirement checkpoint
без сохранённого IPv4 отклоняется; адрес нельзя восстановить из изменяемой строки exit.
Только внутренний этап `retire_unpublish` может отключить
узел; worker сериализуется с изменениями топологии и deployment drain в порядке
`topologyMu` → блокировка cloud worker. Неизвестные внутренние ошибки остаются общими для UI; журнал
записывает безопасный код, фазу и длительность без текста ошибки или тела запроса.
Источники: [действие операции](../internal/cloud/service.go),
[Admin API](../internal/adminapi/cloud.go),
[защита exit во время retirement](../internal/db/repo_reinstall_guard.go),
[защита последнего exit](../internal/db/repo_exit_nodes.go).

Раздел «Сервис» читает баланс и начисления через `GET /account`; наружу передаются
только эти суммы и время проверки, без имени, email и ACL аккаунта. Суммы показываются
в том виде, как их возвращает Vultr; срок до исчерпания средств не прогнозируется.
Источник: [account.go](../internal/cloud/account.go),
[документация Vultr](https://docs.vultr.com/platform/billing/view-payment-history).

GET/DELETE без параметров тела отправляются без body и Content-Type. Значение JSON
`null` в теле GET приводит к HTTP 400 `Invalid JSON` у `/ssh-keys` и `/firewalls`,
хотя `/os` его принимает. Регрессия: `TestVultrReadRequestsHaveNoJSONBody` в
[errors_test.go](../internal/cloud/errors_test.go).
