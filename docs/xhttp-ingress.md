# Постоянный XHTTP/TLS-вход

Основной VPN — Nginx TLS/HTTP2 → loopback XHTTP/VLESS основного relay. Экспериментальный отдельный процесс снят с публикации; его старые spec и резервная метаинформация остаются читаемыми для безопасного обновления. Границы — [ADR 0017](adr/0017-xhttp-ingress.md), клиентский контракт — [HAPP](happ.md).

## План и команды

Публичный ingress-plan не содержит токенов, UUID и ключей. Пример:

```json
{
  "domain": "example.com",
  "public_host": "BRIDGE_IP",
  "email": "admin@example.com",
  "path": "/connect",
  "fingerprint": "firefox",
  "experimental_fingerprint": "firefox",
  "backend_port": 18080,
  "gateway_port": 18081,
  "status_port": 18082,
  "experimental_port": 5543,
  "staging_port": 18443
}
```

При прямом подключении `public_host` задаёт IP bridge, а `domain` — SNI и имя сертификата. Домен может сохранять прежний HTTPS-вход подписки; HTTP-01 должен по-прежнему доходить до bridge:80. Если публичный адрес задан доменом, он должен указывать на bridge. AAAA не публикуется без проверки IPv6. До запуска подготовьте правила firewall сервера и провайдера: TCP/80 для ACME, TCP/443 для основного входа, `staging_port` для приёмки для временной приёмки. `experimental_port` и `status_port` остаются метаинформацией старых установок; новый эксперимент не создаётся. Ingress-команда не меняет firewall; локальные backend/status-порты наружу не открываются. Домен регистрируется отдельно от установки, только после согласования конкретной цены и условий владельцем.

Необязательный `fingerprint` в плане задаёт `chrome` (по умолчанию) или `firefox` для основного входа. `experimental_fingerprint` сохраняется только при чтении старых планов. Эти поля управляют клиентским экспортом, а не сертификатами сервера. В `/client` резервные `public_entries` для опубликованного XHTTP используют свой `host` и `xhttp_tls_port`, сохраняя SNI основного входа; записи без TLS-порта не экспортируются для этого транспорта.

```sh
./ultra-install ingress -action stage -plan ingress.json -host BRIDGE -identity KEY -known-hosts KNOWN_HOSTS -relay-binary ./ultra-relay
./ultra-install ingress -action status -plan ingress.json -host BRIDGE -identity KEY -known-hosts KNOWN_HOSTS
```

Команды всегда используют строгую проверку SSH host key. `stage` готовит новый backend и HTTPS на временном порту, но `published: false` сохраняет выбор основного транспорта подписки. Старый рабочий TLS listener остаётся до переключения. Если основной `primary_xhttp` уже опубликован, `stage` отклоняется до изменения файлов; для смены опубликованного входа используется отдельный cutover. Команда `experiment` отклоняется: эксперимент больше не создаётся.

Установщик сохраняет собственные хеши конфигураций: чужие или изменённые вручную файлы не перезаписываются. Перед применением проверяет spec, TLS и `nginx -t`; повтор без изменений не делает reload. Резервные бинарники и spec сохраняются на сервере в закрытом `/var/lib/ultra-ingress`. Конфигурация включает стабильный путь; случайная генерация при повторном применении запрещена.

## Сертификаты

Nginx получает сертификат ACME webroot и выполняет graceful reload при продлении. Основной relay не перезапускается. Прежние challenge-пути сертификата бота продолжают работать через существующий HTTPS ingress; прежний standalone challenge переводится на webroot перед установкой постоянного HTTP listener.

Старые отдельные копии сертификатов эксперимента не обновляются этой ролью. Проверять `certbot renew --dry-run` для действующих общих сертификатов. Staging-сертификат не устанавливать вместо рабочего.

## Проверки и переход

До активации проверить внешний TLS на временном порту, Auto и страны, TCP и UDP/XUDP, DNS, обновление подписки при включённом Android HAPP, повторное подключение. Серверный `/v1/health.public_ingresses` проверяет основной вход; это не клиентская приёмка.

Перед общим переходом `-action notice` использует `notice_key` и `notice_text` из публичного плана: сообщение ставится в существующую очередь бота только активным владельцам подписок с Telegram-привязкой. Повтор одного ключа не дублирует очередь в переходном периоде. Затем:

```sh
./ultra-install ingress -action activate -plan ingress.json -host BRIDGE -identity KEY -known-hosts KNOWN_HOSTS
```

`activate` отключает прежние публичные REALITY listeners, переносит HTTPS на 443 и публикует XHTTP как основной. Пользователю требуется обновить прежнюю подписку, перевыпуск ссылки не нужен. При ошибке или превышении пяти минут использовать `-action rollback`: он восстанавливает выдачу профилей на ранее рабочий TLS endpoint, а не объявляет возврат REALITY восстановлением VPN. Клиенту после смены endpoint может потребоваться обновление подписки.

Откат сохраняет текущий локальный вход экспериментального шлюза и его публичное описание, а также Nginx с webroot для ACME. Из сохранённой конфигурации возвращается только ранее рабочий TLS endpoint; остальные текущие параметры bridge сохраняются.

Если сохранённая конфигурация уже публиковала `primary_xhttp`, откат возвращает именно его, включая порт и клиентский `fingerprint`. Наличие дополнительного `public_xhttp_tls` listener не делает его проверенным резервом. Для старых снимков без опубликованного основного входа используется прежний `public_xhttp_tls`. Перед новым переходом комплект отката должен соответствовать последнему варианту, принятому на клиенте; исторические снимки сохраняются отдельно.

При откате проверить общий URL, UUID и обе страны; не менять квоты или токены вручную. Отказ всего IP/bridge и режим белых списков этот выпуск не устраняет.

## Снятие эксперимента

Обычный upgrade автоматически выполняет эту очистку после read-only проверки
доменов и до снимков нового runtime, capture и замены бинарников. Используются
текущий fleet lease и отдельный immutable ingress job: повторного CLI/захвата
блокировок нет. Наличие descriptor, runtime-файлов, записей владения или журнала
делает очистку обязательной; при ошибке metadata, ownership или кеша upgrade
завершается до активации. Старый relay и bot должны уметь обновить кеш после
снятия descriptor; недоступный bot/БД не обходятся.

Отдельно ту же операцию можно выполнить командой:

```sh
./ultra-install ingress -action retire-experiment -config install.config
```

Перед запуском оператор проверяет текущие приватные файлы и при необходимости
обновляет каноническую конфигурацию и резервную метаинформацию:

1. В `/etc/ultra-recovery/deployment.json` поле `ingress` должно уже содержать
   подтверждённые `experimental_port` и `status_port` из управляемого descriptor.
   Эти метаданные не подтверждают, что экспериментальный listener активен, и не
   являются источником для его автоматического восстановления.
2. В обязательных `state_paths` и `artifact_paths` из
   `/etc/ultra-recovery/backup.json` и канонического плана не должно быть файлов,
   которые удалит операция: descriptor, spec и unit эксперимента. Сначала сохранить
   рабочий backup и исправить перечень; служба очистки сама его не переписывает.
3. Установить версию relay с отключённой выдачей эксперимента. Проверить обычные
   URI и HAPP JSON и доступность полного обновления кеша бота.
4. Запустить отдельную команду. Она проверяет хеши descriptor, spec и unit по
   `/var/lib/ultra-ingress/managed.json`, сохраняет приватный журнал
   `/var/lib/ultra-ingress/retired-experiment.json` и удаляет descriptor через
   crash-safe реестр владения. После этого ожидает сохранённый кеш
   `/var/lib/ultra-bot/subscriptions.json`: каждый профиль должен иметь
   `confirmed_at` после начала операции и не содержать метку эксперимента.
   Ошибка БД, неполный/старый кеш или дрейф файла прерывают очистку до остановки.
5. В точном owned renewal hook удаляется известная ветка рестарта эксперимента;
   прочие команды Nginx и bot сохраняются. Неизвестная ветка или drift hash
   прекращают очистку. Только после этих проверок останавливается и отключается
   `ultra-experimental.service`, удаляются принадлежащие установщику spec и unit,
   обновляется systemd. Повтор продолжает тот же журнал и допускает уже удалённые
   файлы при отсутствии записи владения. Проверить основной VPN, обновление
   подписки и следующий backup.

Команда сохраняет основной `gateway_vless_port`, Nginx, shared ACME сертификаты,
учётные записи и старое поле `experimental_profile_file`. Последнее можно убрать
из исходного spec при следующем проверенном обновлении. Если эксперимент никогда не устанавливался, операция пропускает очистку runtime
и удаляет только известную owned ветку renewal hook, если она сохранилась. Новый
шаблон hook больше не содержит рестарт эксперимента. Копии бинарника и
сертификатов в `/opt/ultra-experimental` и `/etc/ultra-experimental` прежняя роль
создавала без хешей владения: эта операция их не удаляет. Их удаление требует
отдельной проверки происхождения и резервного inventory; массовое удаление
каталогов недопустимо. Прежний транспортный режим и разбор legacy spec остаются
для восстановления, а создание нового эксперимента запрещено.
