# Постоянный XHTTP/TLS-вход

Основной VPN — Nginx TLS/HTTP2 → loopback XHTTP/VLESS основного relay. Отдельный экспериментальный процесс принимает TLS/XHTTP и передаёт исходный VLESS с PROXY protocol в loopback-вход основного relay. Учёт и авторизация остаются в одном месте. Границы — [ADR 0017](adr/0017-xhttp-ingress.md), клиентский контракт — [HAPP](happ.md).

## План и команды

Публичный ingress-plan не содержит токенов, UUID и ключей. Пример:

```json
{
  "domain": "example.com",
  "public_host": "BRIDGE_IP",
  "email": "admin@example.com",
  "path": "/connect",
  "fingerprint": "firefox",
  "experimental_fingerprint": "firefox",
  "backend_port": 18080,
  "gateway_port": 18081,
  "status_port": 18082,
  "experimental_port": 5543,
  "staging_port": 18443
}
```

При прямом подключении `public_host` задаёт IP bridge, а `domain` — SNI и имя сертификата. Домен может сохранять прежний HTTPS-вход подписки; HTTP-01 должен по-прежнему доходить до bridge:80. Если публичный адрес задан доменом, он должен указывать на bridge. AAAA не публикуется без проверки IPv6. До запуска подготовьте правила firewall сервера и провайдера: TCP/80 для ACME, TCP/443 для основного входа, `staging_port` для приёмки и `experimental_port` для эксперимента. Ingress-команда не меняет firewall; локальные backend/status-порты наружу не открываются. Домен регистрируется отдельно от установки, только после согласования конкретной цены и условий владельцем.

Необязательный `fingerprint` в плане задаёт `chrome` (по умолчанию) или `firefox` для основного входа. `experimental_fingerprint` переопределяет его только для отдельного эксперимента; без переопределения используется значение основного входа. Эти поля управляют клиентским экспортом, а не сертификатами сервера. В `/client` резервные `public_entries` для опубликованного XHTTP используют свой `host` и `xhttp_tls_port`, сохраняя SNI основного входа; записи без TLS-порта не экспортируются для этого транспорта.

```sh
./ultra-install ingress -action stage -plan ingress.json -host BRIDGE -identity KEY -known-hosts KNOWN_HOSTS -relay-binary ./ultra-relay
./ultra-install ingress -action experiment -plan ingress.json -host BRIDGE -identity KEY -known-hosts KNOWN_HOSTS
./ultra-install ingress -action status -plan ingress.json -host BRIDGE -identity KEY -known-hosts KNOWN_HOSTS
```

Команды всегда используют строгую проверку SSH host key. `stage` готовит новый backend и HTTPS на временном порту, но `published: false` сохраняет выбор основного транспорта подписки. Старый рабочий TLS listener остаётся до переключения. Если основной `primary_xhttp` уже опубликован, `stage` отклоняется до изменения файлов; дальнейшие пробы выполняются отдельным экспериментом. `experiment` меняет только отдельный сервис и descriptor; основной spec не переписывается.

Установщик сохраняет собственные хеши конфигураций: чужие или изменённые вручную файлы не перезаписываются. Перед применением проверяет spec, TLS и `nginx -t`; повтор без изменений не делает reload. Резервные бинарники и spec сохраняются на сервере в закрытом `/var/lib/ultra-ingress`. Конфигурация включает стабильный путь; случайная генерация при повторном применении запрещена.

## Сертификаты

Nginx получает сертификат ACME webroot и выполняет graceful reload при продлении. Основной relay не перезапускается. Прежние challenge-пути сертификата бота продолжают работать через существующий HTTPS ingress; прежний standalone challenge переводится на webroot перед установкой постоянного HTTP listener.

Эксперимент получает сертификат в собственный каталог с ограниченными правами. Его deploy-hook проверяет пару ключ/сертификат и перезапускает только экспериментальный процесс. Проверять `certbot renew --dry-run` отдельно для нового и прежнего сертификата. Staging-сертификат не устанавливать вместо рабочего.

## Проверки и переход

До активации проверить внешний TLS на временном порту, Auto и страны, TCP и UDP/XUDP, DNS, обновление подписки при включённом Android HAPP, повторное подключение. Серверный `/v1/health.public_ingresses` различает основной и экспериментальный вход; это не клиентская приёмка.

Изменение эксперимента должно сохранять основной бинарник, spec и reload count. Ошибочный эксперимент и его перезапуск не прерывают основной поток. Ограничения сервиса: MemoryMax 256M, CPUQuota 50%, TasksMax 64; Достаточность лимитов под нагрузкой проверяется отдельно по согласованию; функциональная готовность не подтверждает запас ресурсов.

Перед общим переходом `-action notice` использует `notice_key` и `notice_text` из публичного плана: сообщение ставится в существующую очередь бота только активным владельцам подписок с Telegram-привязкой. Повтор одного ключа не дублирует очередь в переходном периоде. Затем:

```sh
./ultra-install ingress -action activate -plan ingress.json -host BRIDGE -identity KEY -known-hosts KNOWN_HOSTS
```

`activate` отключает прежние публичные REALITY listeners, переносит HTTPS на 443 и публикует XHTTP как основной. Пользователю требуется обновить прежнюю подписку, перевыпуск ссылки не нужен. При ошибке или превышении пяти минут использовать `-action rollback`: он восстанавливает выдачу профилей на ранее рабочий TLS endpoint, а не объявляет возврат REALITY восстановлением VPN. Клиенту после смены endpoint может потребоваться обновление подписки.

Откат сохраняет текущий локальный вход экспериментального шлюза и его публичное описание, а также Nginx с webroot для ACME. Из сохранённой конфигурации возвращается только ранее рабочий TLS endpoint; остальные текущие параметры bridge сохраняются.

Если сохранённая конфигурация уже публиковала `primary_xhttp`, откат возвращает именно его, включая порт и клиентский `fingerprint`. Наличие дополнительного `public_xhttp_tls` listener не делает его проверенным резервом. Для старых снимков без опубликованного основного входа используется прежний `public_xhttp_tls`. Перед новым переходом комплект отката должен соответствовать последнему варианту, принятому на клиенте; исторические снимки сохраняются отдельно.

При откате проверить общий URL, UUID и обе страны; не менять квоты или токены вручную. Отказ всего IP/bridge и режим белых списков этот выпуск не устраняет.
